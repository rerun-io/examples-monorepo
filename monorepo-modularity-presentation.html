Repeated Patterns Worth Preserving

Keep

Typed config and tyro CLIs

Packages frequently expose dataclass configs and thin tyro wrappers. That is the right public API shape for reproducible demos.

Keep

Gradio as a separate adapter

The best packages put UI code in a dedicated module and keep tools/apps/*.py launchers almost empty.

Keep

Rerun as the visualization contract

Rerun gives CLI and Gradio a shared output target. The strongest abstraction is: computation logs to the active recording context.

Keep

Root dev tasks

lint, typecheck, tests, and deadcode are shared through the root dev feature and PACKAGE_DIR.

Keep

Package-specific environments

Heavy CV stacks need isolation. One prod and one dev environment per package is reasonable given CUDA and model dependency conflicts.

Keep

Example data tasks

Idempotent hf download tasks make demos repeatable without committing large assets.

What Is Not Modular Yet

The repo has many local successes, but the boundaries are not yet uniform enough for a new node to feel obvious.

Surface names drift

API directories alternate between api and apis. Gradio modules alternate between gradio_ui, gradio, and top-level files. One package uses tool/ instead of tools/.

Effect: code review and migration require package-specific memory.

Some API files carry too much responsibility

Several modules combine model loading, workflow orchestration, config, CLI, Rerun logging, and serialization. That makes reuse hard even when the algorithm is valuable.

Effect: every Gradio app and CLI tends to grow custom glue.

Shared glue is copied, not factored

Rerun binary streams, recording IDs, viewer setup, launch boilerplate, and widget-to-config sync appear in multiple packages with small variations.

Effect: improvements and bug fixes do not propagate.

Tests are uneven

Many packages only have import tests. A few packages have behavior and Rerun artifact checks. NodeSpec needs a small required test tier so refactors can be trusted.

Effect: modularization would otherwise be a large, risky rename.

Package metadata is inconsistent

Layout alternates between flat and src/. Some packages specify wheel packages through Hatch; others use setuptools discovery. monoprior includes tools* in installable package discovery.

Effect: installed surfaces are not clearly separated from development launchers.

Pixi has a policy violation

feature.monoprior.tasks.build-wheel and upload-pypi run python -m pip install. That conflicts with the repo rule that dependency management goes through Pixi.

Effect: the build path can escape the locked environment.

Pixi Dependency Shape

For this repo, Pixi is not just a package manager. It is the workspace boundary between incompatible model stacks. The current root feature/env model is mostly correct.

Current shape

  • [feature.common] holds shared CV, Rerun, Gradio, and utility deps.
  • [feature.cuda] centralizes CUDA 12.9 and PyTorch GPU dependencies.
  • [feature.dev] centralizes ruff, pytest, beartype, pyrefly, hypothesis, vulture.
  • Each package gets a prod and dev environment with the same solve group.
  • Package pyproject.toml files mostly stay standard Python metadata.

Recommendation

  • Keep root pixi.toml canonical until Pixi package-local dev/task workflows stabilize.
  • Split shared features only when they represent real responsibility boundaries, not just shorter files.
  • Use package features for package deps, app tasks, data download tasks, and PACKAGE_DIR.
  • Remove pip installs from Pixi tasks. Add build tools as Pixi deps or dedicated build features.
  • Do not adopt UV-backed Kornia tasks because this repo explicitly forbids UV.

Pixi issue read: Discussion #4956 says multi-package workspace work is in scope, but the maintainer pointed to pixi-build and warned to expect changes. Issue #4721 proposed package dev dependency collection, but solve group behavior and package-local task behavior remain unsettled. So the practical strategy is to keep root-level dependency/task orchestration now, and design the code layout so it can move later without changing public node contracts.

Feature Responsibility What belongs What does not belong
common Lowest common runtime surface numpy, scipy, jaxtyping, rerun, simplecv, huggingface_hub Model-specific frameworks or optional app deps that only one package needs
gradio-app or keep in common Interactive UI surface gradio, gradio-rerun, shared app launcher helpers Model weights, data downloads, package-specific widgets

External References

Kornia

Useful for domain API layout

kornia/kornia is a Python-first library with one main package split by domains such as geometry, filters, feature, io, models, and augmentation.

Take the clear domain namespaces and test/docs discipline. Do not copy the monolithic distribution shape or UV-backed Pixi tasks.

Kornia-RS

Useful for workspace modularity

kornia-rs is closer to what this repo needs: core crates, standalone examples, Python bindings, C++ bindings, docs, tests, and Pixi tasks.

Take the idea of default core members, standalone examples, and explicit binding boundaries. Avoid native complexity unless needed.

create-node

Useful as the local abstraction

The create-node skill already names the right unit: one reusable CV node with typed config/result, CLI, Gradio, Rerun, examples, and Pixi tasks.

Tighten it before scaling: require log_result, define config categories, document concurrency, and add test tiers.

Adopt

  • Examples as first-class workspace units, like Kornia-RS examples/*.
  • Umbrella plus direct module access, where users can either run an app or import a node directly.
  • Public APIs arranged by domain, not by how the demo happened to grow.
  • Default checks that do not accidentally build every heavyweight demo.

Do not adopt

  • UV workflows from Kornia, because this repo requires Pixi and forbids UV.
  • One giant Python package for all examples.
  • Rust/PyO3 binding complexity unless a specific package has native shared core needs.
  • Broad root-level tests that hide local package ownership.

Kornia Decision

Kornia is useful, but not as a complete template. kornia/kornia and kornia-rs teach different lessons.

How much to copy from each repo
Repo What it is Good reference for Bad reference for Apply here
kornia/kornia One Python library package with domain modules, docs, tests, benchmarks, and Pixi dev tasks. Public API taxonomy: geometry, filters, feature, models, io, etc. A multi-package examples monorepo. It is not trying to isolate many heavyweight app stacks. Borrow domain naming and testing discipline. Do not copy the one-big-package shape.

What Kornia gets right

  • Users import stable domain namespaces instead of random demo scripts.
  • Docs and tests live at predictable paths.
  • Domain APIs are the public product, not the internal folder history.
  • It separates low-level fast image operations through kornia_rs while keeping higher-level Python APIs in kornia.

What Kornia-RS gets right

  • crates/* are core reusable libraries.
  • examples/* are first-class runnable examples, not hidden inside the core.
  • kornia-py and kornia-cpp are adapters/bindings with their own build surfaces.
  • Pixi tasks expose separate Rust, Python, C++, and CUDA workflows.

Translation for this repo: use Kornia-style domain APIs inside model packages, and Kornia-RS-style workspace boundaries across packages. That means monopriors/depth, monopriors/normals, and monopriors/multiview are library domains, while calibration workbenches and Gradio flows are apps/workflows that depend on those domains.

Shared Language

Use these words consistently. The goal is that a file path, a Pixi task, a test name, and a PR description all point to the same architectural idea.

Workflow is the primary term. Use it for the thing a user is trying to accomplish. Use pipeline only when you specifically mean the implementation path inside code, where objects move from one function or node to the next.

GUI vs CLI rule

GUI and CLI are adapters over the same node or workflow. They should not duplicate model logic, step ordering, or final Rerun logging.

  • CLI owns paths, batch flags, and RerunTyroConfig.
  • GUI owns widgets, uploads, session state, and streaming bytes.
  • Both call the same node or workflow function and the same log_result().
  • If behavior differs between GUI and CLI, the difference should be explicit adapter behavior.

App vs node rule

A node is reusable machinery. An app is the user-facing experience built from machinery.

  • One model with one typed result is probably a node.
  • Several nodes plus user decisions is probably an app/workflow.
  • A data converter can be a node if it is reusable across workflows.
  • A workbench with tabs, examples, and comparison views is an app.

Testing rule: every new node gets T0, T1, and T2. Every public CLI gets T3. GUI callback tests are for reusable node GUIs. Full browser tests are reserved for important apps because they are slower and more fragile.

Node Contract

The right abstraction is not "a Gradio app" and not "a Pixi environment." It is a typed, reusable CV node. CLI and Gradio are adapters. Apps are orchestrators.

Config Dataclass, jaxtyping where needed, field docs, tyro-compatible.
Node Loads model once, owns computation, logs intermediate details when verbose.
Result Dataclass or NamedTuple with typed arrays and domain names.
Rerun log_result and create_blueprint shared by CLI and Gradio.
Adapters CLI loads paths. Gradio syncs widgets and streams. Apps compose nodes.

Example Package Layout

Yes: migrate one package at a time. The repo should not try to normalize every package in one pass. Pick one package, define its local node/app boundary, add tests around that boundary, then carry the pattern to the next package.

Recommended first package: pysfm

Start here if the goal is to prove the layout with low risk. pysfm already has a class-based VideoToImageNode, thin launchers, and Gradio node files. It is close enough that the migration is mostly tightening the contract.

  • Add the missing shared log_video_to_image_result().
  • Split one large API module only after a characterization test exists.
  • Use it as the canonical package template for future nodes.

Recommended second package: monoprior

Move here once the layout is proven. monoprior has the highest abstraction payoff because VGGT calibration already wants separate VGGT, SAM3, metric depth, alignment, and fusion responsibilities.

  • Keep the current calibration app as the user-facing orchestrator.
  • Extract reusable nodes underneath it one at a time.
  • Do not rename every old file before the node contracts are green.

Package-first rule: inside one package, finish one vertical slice before moving on: typed API, Rerun logging, CLI, Gradio UI, Pixi tasks, and tests for one node. Avoid repo-wide mechanical renames until at least two packages follow the same shape.

Model Packages Vs App Packages

monoprior is currently doing two jobs: it is a library of reusable geometric prior models, and it is also a collection of end-user apps. That is why it feels vague. I would split the responsibilities conceptually first, then physically when tests make it safe.

Avoid

One giant models package

A single models package sounds clean, but it will quickly inherit every heavy dependency: SAM, VGGT, MoGe, pose, TensorRT, SfM, CUDA kernels. That creates a slow, fragile solve and makes small apps pay for unrelated model stacks.

Use carefully

Domain model libraries

Group reusable model wrappers by dependency and domain: depth/normal/multiview priors, segmentation, pose, SfM, VRS/data. These packages expose typed nodes and results, but they do not own large composite apps.

Prefer

Workflow app packages

Apps depend on one or more model libraries and own the user experience: Gradio layouts, CLI workflows, example data, Pixi tasks, and orchestration. This makes "what does this package do?" much easier to answer.

Three possible shapes for monoprior
Shape Pros Cons Recommendation
Keep monoprior as everything Few package moves. Existing imports and Pixi tasks keep working. The package keeps accumulating depth, normals, multiview, calibration apps, data tools, and UI glue. Acceptable short term, but document internal boundaries immediately.
Split into monopriors library plus monoprior-apps Clear distinction between reusable model nodes and user-facing workflows. Some import churn. Apps still share the same broad model dependency family. Best next step for this repo.
Split every model family into separate packages now Maximum isolation and clear dependency ownership. High migration cost. Easy to over-split before real reuse patterns are known. Do only after the library/app split exposes real dependency pressure.

Responsibility boundaries

  • cv-demo-core: no heavyweight model deps. Only shared Rerun/Gradio launch glue, typed helpers, example-data utilities, and maybe generic serialization helpers.
  • monopriors: model wrappers and reusable nodes for geometric priors. It can expose CLIs for each node, but not the big user-facing workbench apps.
  • monoprior-apps: calibration workbench, depth compare, depth alignment UI, and any app that composes multiple monopriors nodes.
  • sam3-rerun, wilor-nano, sapiens2-pose: stay separate because their model stacks and user surfaces are different enough.
  • mv-api, slam-evals, pyvrs-viewer: data/catalog/eval packages, not model packages.

Pragmatic path: do not physically split monoprior first. First create the internal layout as if the split already happened: monopriors/depth, monopriors/normals, monopriors/multiview, monopriors/apps. Once imports and tests are stable, moving apps into monoprior-apps becomes a small packaging change instead of an architecture rewrite.

Model libraries

Own reusable inference units: configs, model loading, typed results, and Rerun logging. They may expose simple demos, but they should not become workbench packages.

Examples: monopriors, sam3-rerun, wilor-nano, sapiens2-pose.

Data and artifact packages

Own reading, conversion, synchronization, catalogs, and artifact schemas. They should stay as dependency-light as possible so many apps can use them.

Examples: pyvrs-viewer, egoexo-forge, slam-evals, parts of mv-api.

App/workflow packages

Own end-user experiences: Gradio layout, CLI workflows, orchestration, example datasets, Pixi tasks, and Daggr graphs.

Examples: future monoprior-apps, calibration workbench, full exo/ego app.

Rule of thumb: if a package answers "how do I run this model?", it is a model library. If it answers "how do I turn this dataset into an artifact?", it is a data package. If it answers "how do I complete this user workflow?", it is an app package.

Model Inventory And Placement

This is the concrete split I would use to decide where each thing lives. A "model" here means either a learned checkpoint runtime or a reusable algorithm runtime. Full user journeys stay outside those model homes.

Placement rule: model packages own weights, model construction, runtime configs, typed result objects, and the reusable node call. App packages own Gradio screens, CLI workflows, dataset choices, Rerun sessions, and composition across multiple nodes. Data and eval packages own readers, converters, catalogs, metrics, and artifacts.

Model Pattern Options

The cleaner choice is one style everywhere: explicit config-driven node classes. Catalogs can list presets for CLI and Gradio, but catalogs should not become hidden runtime factories or make unrelated workflows look interchangeable.

No core model factories: every model node gets an explicit Config, explicit node class, and typed Result. Construction is direct or through from_config(config). Package-local catalogs are declarative metadata for presets, docs, dropdowns, and CLI choices; they do not replace the explicit class API.

Unified Style Decision

The core API is explicit. A user or app should be able to see the model family from the class name, the runtime choices from the config, and the artifact contract from the result type. 

config = MogeV2MetricDepthConfig(device="cuda")
node = MogeV2MetricDepthNode.from_config(config)
result = node.predict(image)
  • One style: explicit Config, explicit node class, typed Result.
  • Catalogs: metadata for presets, UI dropdowns, CLI choices, docs, and example task names.
  • No runtime factory: no global get_model("moge-v2") as the architecture.
  • Composition: apps wire concrete nodes together instead of asking a broad catalog for runtime objects.
  • Shared contracts: reuse DepthResult, PoseResult, SegmentationResult, etc. only when the artifact contract is truly shared.

Kornia Pattern

Kornia models are organized by family: SAM, RT-DETR, depth estimation, segmentation, EfficientViT, processors, and related utilities. The useful part for this repo is the family folder, explicit model class, config object, and high-level wrapper outside the raw model family.

  • Borrow: family folders, thin public __init__ exports, config dataclasses, model/preprocessor/postprocessor split.
  • Borrow: builders for complete runnable pipelines when a demo needs model plus preprocessing plus postprocessing.
  • Translate: Kornia-style preset constructors become package-local catalog entries here.
  • Avoid: inconsistent constructor names, runtime factories, and ad hoc pretrained metadata.
  • Best fit here: monopriors/depth, sam3, wilor_nano, and sapiens2_pose.

Modular MAX Pattern

MAX model bring-up is strongest as a lifecycle reference: classify the model, adapt config and weights, isolate graph changes, then validate through the same runtime path. It is production LLM serving oriented, so copy the discipline, not the machinery.

  • Borrow: model introduction ladder: wrapper only, adapter only, changed component, new model package, custom kernel escape hatch.
  • Borrow: separate config adapter, checkpoint adapter, compute graph/model, pipeline/runtime, and architecture metadata.
  • Avoid: KV-cache/tokenizer/serving assumptions for normal CV demos.
  • Best fit here: DPVO, MASt3R-SLAM, Sapiens TensorRT, Gaussian renderer, any checkpoint-heavy model.

Transformers Pattern

The Transformers tenets are the clearest warning against over-abstraction: make model code readable, standardize public surfaces, keep configs and processors explicit, and avoid hiding model-specific behavior behind clever base classes.

  • Borrow: explicit design tenets, stable configs, processor/model/result split, minimal user API, compatibility tests.
  • Translate: Auto*-style discovery becomes declarative catalogs, not runtime factories.
  • Avoid: remote-code loading, huge global registries, runtime factories, and compatibility layers with no expiry plan.
  • Best fit here: model packages that need stable user-facing presets, not one-off workflows.

MVAPI Multi-View Pose Pipeline

MVAPI is the best package to use as the next modularity exercise because it is useful, concrete, and currently mixes several responsibilities in one model-backed stage. The goal is not to split it into many tiny files. The goal is to make each computational boundary obvious and keep image tensors on the right device until a boundary truly needs CPU data.

Recommended direction: treat MVAPI as an app/workflow composed from nodes. Keep mv-api as the package that owns the exo/ego pose application, but move the reusable pieces into explicit node contracts: scene source, calibration, pose tracking, triangulation, ego reprojection, hand refinement, and Rerun artifact logging.

Current Shape

1

Scene setup

ScenePreparationNode calls the selected dataset config, logs the exo/ego scene shell, and returns synchronized timestamps plus Rerun log paths.

2

Camera choice

run_model_backed_pipeline chooses dataset cameras when available, otherwise reads calibration frames and runs MultiViewCalibrator.

3

MultiviewBodyTracker runs YOLOX, RTMPose, optional WiLoR, temporal extrapolation, and triangulation into COCO-133 3D keypoints.

4

Proposed Component Split

Source node

ExoEgoFrameSourceNode owns dataset setup, stream sync, timestamp selection, and frame batches.

  • Returns FrameBatch with exo frames, ego frames, timestamps, stream names, and optional camera params.
  • Can expose torch GPU tensors when the Rerun data loader or TorchCodec path can provide them.

Calibration node

MultiviewCalibrationNode owns camera estimation and conversion back to native video resolution.

  • Input is a small calibration batch, not the whole application config.
  • Result is CalibrationResult: exo cameras, ego cameras, optional point cloud, optional mesh.

Box detector node

PersonBBoxDetectorNode owns only person box detection for selected exo cameras.

  • Input is a torch RGB frame batch from the catalog loader.
  • Result is boxes, scores, labels, camera names, and timestamp. RTMPose is a separate keypoint node.

Triangulation node

PoseTriangulationNode owns projection matrices, min-view policy, temporal state, and 3D confidence filtering.

  • Input is typed 2D keypoints plus cameras.
  • Result is Pose3DFrameResult with xyzc, extrapolated projections, and validity masks.

Ego projection node

EgoPoseProjectionNode owns projecting exo-fused 3D pose into ego cameras.

  • Applies depth and image-bound validity masks.
  • Can call the hand refinement node on ego crops without depending on the full pipeline.

Artifact node

MVAPIRerunLogger owns Rerun entity paths, annotation context, debug layers, and blueprint decisions.

  • Consumes typed results from nodes.
  • Allows compute tests to run without initializing Rerun.

First Primitive Node: Person Boxes

You are right: if a node means one responsibility, then the first node is not "2D pose." It is person bounding-box detection. The catalog path should produce a torch frame batch, the box detector should return torch boxes, and a later composed stage can feed those boxes into RTMPose.

Correct split: PersonBBoxDetectorNode detects people. BodyKeypoint2DNode estimates keypoints inside supplied boxes. CatalogPose2DStage or MVAPIPoseWorkflow composes detector plus keypoint node plus optional hand refinement.

Person Box Request

@dataclass(slots=True)
class PersonBBoxRequest:
    timestamp_ns: int
    camera_names: list[str]
    rgb_chw: UInt8[Tensor, "n_views 3 h w"]

@dataclass(slots=True)
class PersonBBoxResult:
    boxes_xyxy: Float32[Tensor, "n_views max_dets 4"]
    scores: Float32[Tensor, "n_views max_dets"]
    labels: Int[Tensor, "n_views max_dets"]
    valid: Bool[Tensor, "n_views max_dets"]
    timestamp_ns: int
    camera_names: list[str]

Usage From Catalog

source = CatalogExoFrameSourceNode.from_config(source_config)
detector = PersonBBoxDetectorNode.from_config(
    PersonBBoxDetectorConfig(model="yolox", device="cuda")
)

for frame_batch in source:
    boxes = detector.run(
        PersonBBoxRequest(
            timestamp_ns=frame_batch.timestamp_ns,
            camera_names=frame_batch.camera_names,
            rgb_chw=frame_batch.rgb_chw,
        )
    )
Person box node boundary decisions
Boundary Decision Why
Input UInt8[Tensor, "n_views 3 h w"] Matches the catalog dataloader's decoded RGB CHW direction and keeps the first interface PyTorch-first.
Device Configured and checked at runtime, not encoded in the type Jaxtyping can express dtype and shape; device is a runtime property like tensor.device.type.
Output Padded torch tensors plus a boolean validity mask Different cameras can have different detection counts; padded tensors batch cleanly for downstream nodes.
Backend today YOLOX/RTMLib adapter hidden behind the node If RTMLib still requires NumPy BGR, the adapter performs that conversion locally. The public node stays torch-first.
Backend later Torch-native detector with the same request/result The workflow should not change when the detector implementation changes.

What This Is Not

Not RTMPose

RTMPose belongs in BodyKeypoint2DNode, which consumes boxes and frames.

Not tracking

Temporal extrapolation and box reuse belong in a tracker or workflow policy layer.

Not logging

Rerun conversion and columns belong in MVAPIRerunLogger.

Torch vs NumPy Boundary

Keep on GPU as long as possible

If the Rerun data loader provides GPU torch tensors, the source contract should preserve them. The pipeline can then avoid repeated np.asarray, BGR/RGB copies, and CPU round trips for model inference. 

@dataclass(slots=True)
class FrameBatch:
    timestamp_ns: int
    exo_rgb: UInt8[Tensor, "n_views h w 3"] | None
    exo_bgr_np: list[UInt8[ndarray, "h w 3"]] | None
    ego_rgb: UInt8[Tensor, "n_ego h w 3"] | None
    cameras: CameraBatch | None

Convert only at adapter edges

Some dependencies still want NumPy or CPU OpenCV arrays: RTMLib, Open3D, Rerun logging, and some SimpleCV geometry helpers. That is fine if the conversion happens in named adapters instead of being scattered through the app. 

frames = source.next(timestamp_ns)
boxes = person_box_node.run(frames.exo_rgb)
pose2d = body_keypoint_node.run(frames.exo_rgb, boxes)
pose3d = triangulation_node.run(pose2d, cameras)
ego_uv = ego_projection_node.run(pose3d, ego_cameras)
rerun_logger.log_frame(frames, pose2d, pose3d, ego_uv)
Boundary policy for MVAPI data types
Layer Preferred internal type Allowed conversion point
Frame loading torch.Tensor on GPU when available, otherwise typed NumPy fallback Only the source node decides how frames are decoded and batched.
Model inference Backend-native tensor type: torch for torch models, NumPy only for ONNX/RTMLib adapters that require it Inside the model adapter node, with one helper such as frames.to_rtmlib_numpy().
Geometry One explicit choice per node. Prefer torch if projection and triangulation are part of the GPU path. At the triangulation/projection node boundary, not inside app orchestration.
Rerun logging CPU arrays accepted by Rerun archetypes Only in MVAPIRerunLogger. Logging should not force the compute path to be CPU-first.
Open3D fusion NumPy/Open3D CPU data Keep this in a calibration artifact adapter; do not leak it into pose tracking.

Target Architecture

Use a small set of explicit layers. The value is not the folder names by themselves. The value is that every layer can be replaced or tested independently.

1
Domain data

Typed arrays, paths, camera models, masks, depth maps, videos.

2
Node

One model or algorithm. Real network I/O only.

3
Result

Typed output dataclass with no UI assumptions.

4
Rerun adapter

Blueprints and final result logging.

5
CLI or Gradio

Path loading, widget config, streaming.

6
App

User workflow that composes nodes.

VGGT calibration as the reference split

shared_images
  -> VGGT geometry
  -> SAM3 people masks
  -> Metric depth
  -> Depth alignment
  -> Fusion
  -> Calibration app

VGGT is a multiview node because the model sees all views jointly. SAM3 and metric depth stay single-image nodes because that is their actual model contract. Alignment and fusion are generic utility nodes.

Config categories

  • Model-loading: checkpoint, model name, device, precision. Cache key.
  • Runtime: thresholds, prompts, frame counts, verbose. Per request.
  • Input: paths, uploads, selected examples. Adapter-owned.
  • Rerun: save/connect/spawn, blueprint policy. CLI/app-owned.
  • UI-only: selected tab, status text, examples. Never part of core config.

Shared abstraction should be small: create a tiny monorepo helper package only for launcher and Rerun/Gradio session glue. Keep model factories, CV math, and package-specific data loading out of it. If a helper is broadly useful outside this monorepo, move it to simplecv instead.

Pros, Cons, And Guardrails

Pros

  • Every capability becomes importable, scriptable, and demoable through the same core code.
  • Rerun output is no longer duplicated between CLI and Gradio.
  • Gradio apps become orchestration layers instead of hidden model wrappers.
  • Tests can target stable contracts instead of UI internals.
  • Pixi stays conservative while the code becomes ready for future package-local workflows.

Cons

  • Initial migration is real work, especially for large API files that grew organically.
  • A shared helper package can become a dumping ground if its boundary is not enforced.
  • Gradio singleton caches require clear model-config versus runtime-config separation.
  • Daggr serialization boundaries are still immature compared with typed Python dataclasses.
  • Too many tiny files can hurt readability if split before a second user exists.
Decision guardrails
Question Answer Why
Should every package move to src/ immediately? No Layout normalization is lower value than API/UI/Rerun contract normalization. Do it when touching a package.
Should every demo be a node? No Nodes are reusable units. Apps and one-off conversion tools can stay as apps or CLIs.
Should Gradio config mutate global state? Only model cache state Runtime settings should be per request to avoid cross-session bleed.
Should Pixi tasks move into package pyprojects? Not yet Pixi's package/dev task workflow is still changing. Keep root Pixi canonical.
Should Daggr drive the architecture? No, but support it Typed NodeSpec should be primary. Serialize at Gradio/Daggr boundaries.

Pragmatic endpoint: when someone adds a new capability, they should know exactly where to put computation, config, result types, Rerun logging, CLI, Gradio widgets, examples, Pixi tasks, and tests. That is the modularity win.
