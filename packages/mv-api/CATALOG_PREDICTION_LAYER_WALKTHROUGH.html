High-level Flow

The important mental model is that the catalog remains the source of truth. The new tool does not rebuild the Assembly101 reader directly. It asks the catalog what data exists, builds a dataloader over that registered data, runs MVAPI on decoded EXO frames, writes a prediction RRD, then registers that RRD back to the same catalog segment.

The source recording is never copied into the prediction layer

The prediction RRD contains only the new prediction entities and their static metadata. Rerun catalog layering works because the new RRD uses the same recording id as the selected source segment. The catalog then knows that the prediction file belongs on top of that segment instead of beside it as an unrelated recording.

The dataloader consumes catalog data directly

The pipeline does not go through the old SimpleCV interface to materialize the dataset. SimpleCV is used to mount/register and expose the Rerun catalog. The actual samples come from Rerun's experimental dataloader API over catalog-backed streams.

The inference surface stays MVAPI-native

Once frames are decoded, the tool converts them into the image format expected by MVAPI and calls the existing MultiviewBodyTracker. That keeps model loading, detection, pose prediction, tracking, triangulation, and the current upper-body filter aligned with the existing oracle pipeline.

1. Catalog Stuff

What gets mounted

The tool mounts the full ExoEgo Forge catalog using SimpleCV's catalog helper. In the v1 design, the catalog is registered broadly, but inference is intentionally scoped to one default Assembly101 segment so the run is inspectable.

  • Catalog root: /mnt/8tb/data/exoego-forge-catalog
  • Dataset: assembly101
  • Default row id: 120
  • Default sequence key: all/nusar-2021_action_both_9034-c02b_9034_user_id_2021-02-04_160111

Why row 120

The default row is not meant to be semantically special. It is a practical default chosen because it has the expected schema and usable video samples. Earlier rows can expose the schema while still producing null samples for the video fields, which is not a valid inference input.

The v1 contract is intentionally loud: if the chosen segment does not provide usable VideoStream:sample data for the discovered EXO cameras, the tool fails instead of silently falling back to another path.

Catalog mount

SimpleCV mounts the catalog and returns dataset entries that Rerun can serve. This is where the tool gets a catalog-backed handle to Assembly101 rather than manually walking Assembly101 files.

Segment select

The Assembly101 rows are sorted by their sequence key. The configured row id selects one segment. The selected segment provides the source recording id, segment id, and schema.

Camera discovery

The tool reads the catalog schema and finds EXO video sample streams shaped like /world/exo/{camera}/pinhole/video:VideoStream:sample. It then checks that those cameras also have the pinhole and transform data needed for projection and triangulation.

2. Catalog to Data Loader

This is the most catalog-specific part of the pipeline. The goal is to turn registered Rerun catalog streams into a normal PyTorch-style iterator where each sample gives the decoded EXO frames for one shared video_time.

Discover fields

Each EXO camera contributes one Rerun dataloader field for its video sample stream. The field path is catalog-derived, not hard-coded as a fixed camera list.

In practice the default segment exposes eight EXO cameras: C10095 C10115 C10118 C10119 C10379 C10390 C10395 C10404

Choose timestamps

The loader targets exact packet timestamps that all selected EXO streams have in common. This matters because target timestamps are passed into Rerun's fill-latest query path.

A synthetic fixed 30 Hz grid can accidentally ask for filled AV1 packet rows more than once, which can produce duplicate decode inputs. The fix is to use common packet times and then downsample them to the requested approximate frame rate.

Decode frames

Rerun's experimental dataloader decodes the video with VideoFrameDecoder. The keyframe window gives the decoder enough context while the output sample remains tied to the requested video_time.

num_workers=0 keeps the loader simple and avoids multiprocessing surprises while the Rerun dataloader API is still prerelease.

Important timeline detail: predictions should be logged on video_time. Starting at 0s is the correct segment-relative behavior. A decoder keyframe context window, such as 10 seconds, is not a reason to skip the first 10 seconds of predictions.
Loader construction in plain language 
catalog segment
  -> schema says which EXO VideoStream samples exist
  -> calibration check keeps only usable cameras
  -> common video_time packet timestamps become sample index
  -> RerunIterableDataset asks Rerun for decoded frames
  -> PyTorch DataLoader yields one multi-camera sample at a time

3. Inference

Input to MVAPI

Rerun yields decoded image tensors per camera. Before calling MVAPI, the tool converts each camera frame from RGB CHW tensor form into the BGR HWC image layout expected by the tracker.

  • One frame per discovered calibrated EXO camera.
  • All views are used for detection in v1, even though it is slower.
  • The camera list is paired with SimpleCV pinhole parameters for triangulation.

Tracker contract

The tool reuses MVAPI's existing MultiviewBodyTracker. That means this new path is catalog-native at the data access and registration layers, but it does not invent a separate pose model or triangulation algorithm.

  • Mode: wholebody
  • Backend: onnxruntime
  • Device request: cuda
  • Single-person contract for v1.
  • MVAPI upper-body filtering remains in place.

uvc_t Per-camera 2D COCO133 keypoints plus confidence. /world/exo/{camera}/pinhole/pred/mvapi/coco133_uv
xyzc_t Triangulated 3D COCO133 keypoints plus confidence. /world/pred/mvapi/coco133_xyz
Static metadata COCO133 keypoint ids, class ids, and skeleton connectivity. Logged once in the prediction recording before dynamic rows.
Performance expectation: this path is slow because it decodes all EXO videos and runs detector plus pose inference over every selected view. GPU is requested through ONNX Runtime, but some graph nodes can still be assigned to CPU. That is not automatically a bug; the useful checks are whether CUDA execution providers are active and whether GPU utilization rises during pose inference.

4. Layer Re-registration

The output is a normal Rerun recording file, but its identity is chosen carefully so the catalog can treat it as a layer on top of the source segment.

RRD write

The tool creates a recording stream with the prediction application id and the selected source segment's recording id. It logs static metadata, then sends dynamic columns indexed by video_time. 

application_id = "assembly101_mvapi_coco133"
recording_id = source_segment.recording_id
timeline = "video_time"

Catalog registration

After the RRD is written, the tool immediately registers that file back into the selected dataset entry with a layer name. Rerun can then display the source segment and prediction layer together from the catalog. 

dataset_entry.register(
    [rrd_path.resolve().as_uri()],
    layer_name=layer_name,
)
Why same recording id matters

If the prediction RRD uses a different recording id, Rerun sees it as a separate recording. If it uses the source segment's recording id, Rerun can align the prediction entities with the original images, pinholes, transforms, and timelines for that segment.

Debugging Notes

When the loader fails

  • Check that the selected segment has non-null VideoStream:sample values.
  • Check that all discovered EXO cameras also have pinhole and transform components.
  • Check that the target timestamps are exact common packet timestamps, not synthetic times.
  • Keep num_workers=0 while debugging dataloader behavior.

When the layer looks wrong

  • Confirm dynamic logs use the video_time timeline.
  • Confirm the prediction RRD uses the source segment's recording id.
  • Inspect both 2D EXO overlays and the 3D triangulated skeleton.
  • If predicted skeleton color is hard to read, change the logged prediction color at the prediction logging point.

Decoded samples fail with duplicate packet errors. Targeting synthetic timestamps that trigger duplicated fill-latest AV1 packet rows. Use exact common packet timestamps on video_time.
Predictions appear offset or not aligned with video. Rows were logged to the wrong timeline or wrong recording id. Check rr.TimeColumn("video_time", ...) and source recording id preservation.
Catalog viewer shows prediction-only recording. Layer registration did not attach to the source dataset/segment. Verify dataset_entry.register(..., layer_name=...) ran successfully.
Run is much slower than expected. All eight cameras are decoded and processed, detector plus pose runs per view. Watch CUDA provider setup, GPU utilization, decode rate, and per-frame tracker timing.

Minimal Checklist

Before running

  • Pixi environment uses prerelease Rerun and latest SimpleCV git revision.
  • The catalog root is reachable.
  • The selected Assembly101 segment has usable EXO video samples.
  • CUDA provider is available if GPU inference is expected.

After running

  • The output RRD exists under packages/mv-api/artifacts/catalog_layers.
  • The catalog layer is registered under the expected layer name.
  • The Rerun viewer shows original source data plus prediction layer together.
  • Each EXO 2D view shows predicted COCO133 overlays on video_time.
  • The 3D view shows triangulated keypoints from those 2D predictions.
