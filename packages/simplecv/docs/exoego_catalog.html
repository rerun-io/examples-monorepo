Contract

The catalog server scans data/exoego-forge-catalog, registers one Rerun dataset per source dataset, creates one table per mounted dataset, and keeps a full segment blueprint registered for clicked recording_uri links.

The table is an index and preview surface. It is not the source of truth for the full recording layout.

Current invariant Table-card behavior can be optimized for scanning, but clicked recordings must render with the full dataset-specific layout that matches direct RRD viewing.

Dataset vs Table

The word dataset appears in three places, but only one of them is the visible *_table. The catalog registers recordings into a Rerun dataset first, then builds a separate index table from the registered segment metadata.

Source dataset Filesystem grouping of source RRD recordings. data/exoego-forge-catalog/hocap/**/*.rrd
to
Rerun catalog dataset Server-side segment namespace registered with optimized RRD URIs. client.get_dataset("hocap")
to
Catalog table Separate Viewer table used as an index and preview surface. hocap_table
Dataset Owns full RRD segments and the registered per-segment blueprint. Opening a recording_uri goes back to this dataset and should look like direct rerun file.rrd.
Table Owns row fields, schema metadata, and the compact table-card blueprint. It points at dataset segments through recording_uri; it does not replace the dataset.

Catalog Flow

Startup is intentionally two-stage. First the catalog imports optimized RRDs into Rerun datasets. Then it asks each registered dataset for its segment metadata and creates the human-facing *_table.

1. Discover files Find <dataset>/**/*.rrd under the catalog root.
2. Optimize copies Write catalog-compatible RRDs into the cache directory.
3. Register dataset dataset.register(...) imports each optimized RRD as a segment.
4. Register blueprint The full per-segment blueprint is saved as .rbl and set as default.
5. Read metadata segment_table().collect() becomes a pyarrow.Table.
6. Build rows RRDIndexRow values become the displayed table rows.
7. Create table client.create_table(...) stores the schema and appends row columns.

Arrow Tables And Properties

There are two different Arrow-shaped tables in the path. One is Rerun's segment metadata table; the other is the display table we create for the Viewer.

Segment metadata table Read from the registered catalog dataset. This table is input data for indexing.
  • rerun_segment_idRequired Rerun segment id used to build the segment URL.
  • property:info:sequence_keyOptional RRD property; may arrive as a one-item Arrow list.
  • pa.Table.from_batches(...)Normalizes collected record batches before row extraction.
Displayed catalog table Created with a schema and appended columns. This is what appears as *_table.
  • id, dataset, sequence_keyStable row id and human-readable labels.
  • recording_uriBoth the clickable segment URL and the table-card preview source.
  • path, size_bytes, marker_flagLocal diagnostics plus a user-editable flag column.
Schema metadata Table-wide metadata, not a visible row column.
  • rerun:table_blueprintBase64 Rerun blueprint payload for table-card previews.
  • segment_preview_column="recording_uri"Tells Rerun which column opens the segment preview.
  • grid_view_card_title="sequence_key"Uses sequence keys as compact preview card titles.
Field metadata Per-column hints that change how the Viewer treats specific fields.
  • id + SORBET_IS_TABLE_INDEXMarks the stable table index column.
  • marker_flag + rerun:is_flag_columnMarks the boolean flag column for review workflows.
  • property:info:*Properties from segment metadata are read before the display table is built.
Common mix-up The dataset column inside hocap_table is just a string label. The actual Rerun catalog dataset is the separate registered segment collection that recording_uri points back into.

Blueprints

There are two blueprint surfaces. Keeping them separate prevents table-card tuning from changing the clicked recording layout.

Registered segment blueprint

Saved as a temporary .rbl and registered on the dataset. This is the blueprint Rerun applies after opening a recording_uri.

  • 3D view rooted at /.
  • Ego videos arranged on the right when available.
  • Exo videos arranged along the bottom when available.
  • Should preserve the layout of the original recording.

Embedded table-card blueprint

Serialized into Arrow schema metadata under rerun:table_blueprint. This blueprint controls compact preview cards inside each dataset table.

  • 3D preview rooted at / with video subtrees excluded.
  • One 2D preview camera, with assembly101 pinned to ego/e3.
  • video_time selected from 0s to 10s.
  • play_state="playing" and loop_mode="selection".
3D time ranges are intentionally avoided A 3D VisibleTimeRange can make hand keypoints stack over time. The preview window belongs on the TimePanel, not on the 3D view.

Optimization Bug

Raw registration failure mode Registering source RRDs directly can produce incomplete catalog segments. Direct rerun file.rrd may look correct while the catalog segment loses pinholes, camera transforms, 2D keypoints, 3D points, or frustums.
Current fix Register optimized cache copies from ~/.cache/simplecv/exoego-forge-catalog-optimized. Keep optimize_for_catalog enabled unless debugging Rerun catalog import itself.
Why optimization changes catalog behavior
Direct viewer open reads the original recording file. Catalog registration imports that file into a catalog segment representation and derives segment schemas from chunks. rerun rrd optimize rewrites those chunks into a layout the importer indexes correctly.

Troubleshooting

Missing frustums or keypoints
Check optimized registration first. If raw RRDs were registered, catalog segments can be missing visual columns even when the source RRD opens correctly.
Table preview video is black or does not loop
Decode the table blueprint and verify the TimePanel has play_state="playing", loop_mode="selection", and 0s to 10s selected. If the clicked recording works, suspect Rerun table-card preview behavior rather than catalog data loss.
3D hands are stacked through time
Look for a 3D view-level VisibleTimeRange. The current table blueprint avoids it and uses the TimePanel selection instead.
