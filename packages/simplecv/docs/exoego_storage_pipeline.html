Make RRD the canonical working layer, not yet the only ground truth.

The generated RRDs are valuable and should be archived off NVMe, but they are still Silver v0 artifacts. Before raw datasets become disposable, the ExoEgo schema needs a completeness gate that records profile metadata and accounts for important modalities such as HOCap depth, HOT3D objects, masks, sparse point clouds, and dataset-specific text or scene context.

Why this is not canonical yet

Superseded note: this page predates the exoego:v2 rig migration; docs/exoego_schema.md is the live schema authority. The schema-metadata and depth specifics below have been corrected to the current rig layout.

docs/exoego_schema.md defines per-rig metadata as static rr.AnyValues on each /world/rig_NN node (schema_version, reference, num_cameras) — not a flat /world/metadata/* entity. The current viewing/logging path logs core videos, cameras, COCO-133 keypoints, optional MANO, optional environment mesh, and optional depth, but it does not yet emit a broader profile/annotation manifest.

The important distinction is that RRD should become the canonical working format. It should not become the only ground truth until the manifest can say exactly what was included, excluded, or intentionally deferred.

The validation loop is the key change: RRDs become canonical only after the schema gate passes, not merely because ingest completed.

Lessons to keep from the optimization work

  • Copy time is part of validation cost; Assembly101-scale movement is large enough to influence the architecture.
  • NVMe matters most for video decode, VRS preprocessing, depth/point-cloud reads, and RRD writing. It matters less for long-term storage.
  • Validation must inspect RRD entities and components, not just count files.
  • Catalog serving and direct RRD playback can behave differently, so representative viewer smoke tests belong in the gate.

Code direction

Defer or revert benchmark-oriented optimization changes for now. The next code pass should be schema-first: metadata, modality mapping, manifest/exclusion reporting, RRD archive validation, and only then performance cleanup.

Valid optimization takeaways

  • Process-pool conversion with cheap sequence enumeration was the largest structural win.
  • Vectorized JSON/keypoint/camera math and avoiding repeated per-frame object work produced real Assembly101 gains.
  • Capping BLAS-style thread pools avoided worker oversubscription on the 8-worker runs.
  • Video asset caching and timestamp parsing helped, but smaller than the process/parser changes.
  • HOCap staging suffered from many small files; EgoDex ingest suffered from episode video reencoding.

Invalid or deferred lessons

  • Any speedup that came from dropping log_labels is invalid for canonical RRDs.
  • The validator must walk both recording and blueprint stores and require matching keypoint-row totals.
  • Thread-parallel sub-initialization regressed because it fought the worker/thread-pool limits.
  • The next agent should prioritize schema completeness over preserving the current optimization code shape.

Medallion Architecture for ExoEgo

This is closer to a lakehouse flow than a permanent local raw archive. For SimpleCV, the useful working layer is the validated RRD catalog. Raw data can become Bronze by reference only after the RRD manifest proves the needed source modalities are preserved or intentionally excluded.

Layer Definition here Primary storage Retention rule
Bronze external Vendor zips, VRS, MP4/HDF5, URL JSONs, checksums, license notes, and optionally a Hugging Face mirror. Vendor source, HF mirror, or HDD only when needed. Do not retain locally by default. Keep manifests and hashes. Mirror only datasets that are hard to reacquire.
Bronze working Downloaded or mounted raw part actively being converted. NVMe scratch. Delete after RRD validation. This avoids HDD to NVMe copy overhead.
Silver RRD Validated RRD recordings with stable IDs, videos, camera poses, timestamps, labels, and dataset metadata. HDD catalog archive; NVMe only during generation and benchmark runs. Keep. This becomes the canonical SimpleCV/Rerun representation only after schema-completeness validation passes.
Gold serving Catalog indices, optimized RRD copies, viewer blueprints, task subsets, and downstream training/eval manifests. HDD plus local caches. Regenerable from Silver. Keep when expensive or user-facing.
Canonicality gate: before deleting raw, the RRD must include every field we care about for that dataset. EgoDex currently needs a metadata audit because the older converter logged language descriptions, while the current ExoEgo adapter focuses on video, camera, and pose streams.

Proposed Pipeline

1

Acquire to NVMe

Download or mount one active part onto NVMe when it fits. Keep manifests, URLs, checksums, and license notes separately so the raw source remains reproducible.

2

Extract on NVMe

Extract and preprocess in the same working area that ingest will read. This avoids the HDD to NVMe transfer step entirely for newly acquired parts.

3

Preprocess to Silver inputs

Run dataset-specific preparation such as HOT3D VRS to _simplecv MP4 conversion. Keep this on NVMe for active batches.

4

Ingest to RRD

Write the RRDs on NVMe for the hot path. This is the Silver candidate, not a temporary side product.

5

Validate canonicality

Run parity and metadata checks. If a dataset field is missing from RRD, either fix ingestion or keep that raw modality in Bronze.

6

Archive RRD, clear raw

Move validated RRDs to HDD catalog storage. Delete transient raw and extracted files from NVMe unless the raw copy failed the canonicality gate.

EgoDex Flow

EgoDex is the storage driver. The upstream repo describes 829 hours total: 725 hours train, 7 hours test, and 97 hours additional. We ingested only the test set.

Capacity warning: full EgoDex is a bad fit for the current disk state if the plan is to keep compressed downloads, extracted raw MP4/HDF5, and final RRDs together. Treat it as a part-by-part pipeline and decide what must be retained.
Why EgoDex is slower than the other current datasets
The current adapter reencodes each episode video through reencode_video_optimal() during ingest. The test-set run took 13:00.85 for 3,243 episodes. Scaling by upstream hours is only a rough estimate, but it suggests full EgoDex is a many-hour job unless the reencode path is changed or cached.
Storage options to decide before downloading train
  1. Download the zip to HDD, extract one part directly to NVMe, ingest, validate, archive RRD, then delete the NVMe extraction.
  2. Keep extracted raw on HDD only for parts that must remain reproducible from local raw data.
  3. Ingest only priority tasks first, such as robot-relevant training tasks, then expand when storage is added.

HFMount and a Hugging Face Mirror

HFMount can mount Hugging Face dataset repos and Storage Buckets as local filesystem paths. It fetches bytes lazily, which is useful for browsing, selective extraction, and avoiding a full clone. It does not remove the need for NVMe during heavy ingest.

Use case Fit Why Pipeline decision
Browse a remote mirror good Directory listings, metadata checks, and spot reads work through normal file paths. Use for manifests and audits.
Selective raw fetch good Only the files or byte ranges read by the pipeline are fetched, with a local cache. Useful for pulling one HOT3D or EgoDex batch to NVMe.
Direct RRD ingest from mount mixed First reads pay network latency, random I/O is explicitly a weak fit, and ingest may reread large videos or archives. Prefer copy/extract from the mount to NVMe, then ingest locally.
Write canonical RRD outputs bucket only Dataset/model repos are read-only through HFMount; buckets can be read-write. Default write modes have durability and consistency caveats. Write RRDs locally first, validate, then upload/sync as a separate archival step.
Best fit here: use Hugging Face as a Bronze mirror for expensive-to-acquire raw sources and possibly as a distribution point for Silver RRD shards. Use HFMount to inspect and selectively fetch. Do not treat the mount as the high-throughput NVMe working directory.
