mamma — streaming multiview body capture: implementation notes

Interactive RRD comparison: original vs first optimization vs final (3-way) · baseline vs final side-by-side (in-browser Rerun viewers; ~190 MB each, give them a moment) · gate-crossing run (11.79 s) · intermediate optimized run · perf plan

Context. MAMMA is a multiview markerless motion-capture pipeline (CVPR 2026): four synchronized cameras in, full-body SMPL-X meshes out. The research release runs as five separate programs passing files through disk at ~12 seconds per frame. This page documents rewriting it as a single causal streaming process — decode → track → landmarks → triangulate → fit → log, no disk writes in the loop — running at 40.7 ms per frame (~295×, ≥80% of realtime on 4 cameras), with final 3D accuracy validated to 23.3 mm MPJPE against the original's own output. Kept as a running log during development; the full build history lives in the appendix at the bottom.

Why this was possible: the recording is the ground truth

A 295× rewrite is easy to make fast and hard to keep correct — every optimization is a chance to silently break quality. Two Rerun capabilities turned that risk into routine checks:

1. The golden artifact is an RRD, not a metrics file. Before touching anything, one full run of the original pipeline was frozen as a Rerun recording. An .rrd preserves every intermediate as queryable data on a shared timeline — the camera video, every person mask, every 2D landmark, every fitted mesh — not just final numbers. That made validation data analysis instead of guesswork: the 30 mm golden gate every optimization had to pass is computed against it; when masks looked off, the SegmentationImage series was read straight out of two recordings and compared per-frame (IoU 0.999 at stride 1, collapses to 0.17 at stride 4 — which reverted a "passing" default); when SMPL-X params looked wrong on dynamic motion, mesh vertices were diffed frame-by-frame between recordings (11 cm mean divergence — which reverted another). Both regressions had passed the numeric gate; the recordings held the evidence to catch, localize, and prove them.

2. The headless viewer makes "does it actually look right?" scriptable. Rerun 0.33's native ViewerClient.spawn(headless=True) runs a real viewer with no window: load an .rrd, render, save a screenshot. Every change here ended with save → reload → screenshot → inspect, at the same cadence as running the test suite. That loop caught what metrics can't see: a missing transparent-background entry tinting whole frames, H.264 corruption from duplicate timestamps (warmup and timed passes sharing one timeline), masks flickering during fast motion. Render-level regressions became reviewable artifacts instead of "it looked fine on my machine."

Two design rules made the speed trustworthy rather than just fast: (1) a golden gate — every change re-validated against the frozen original output (MPJPE/PVE ≤ 30 mm on crossing_arms; shipped defaults measure 23.3 mm); (2) when a speed lever degraded quality outside what the gate covers, quality won the default: track_stride and fit_stride both shipped at 1 after mask-collapse / dynamic-motion evidence (see the mask validation section and perf-plan round 7), relaxing the wall-time gate to 15 s (≥80% of realtime). The fastest verified configuration (11.76 s, faster than realtime) remains available via flags. What the port gives up by design: causality (no future frames — the original's whole-sequence LBFGS sees the entire clip), and 720p inference instead of 4K.

Deep dives — each optimization, with architecture

1. From a 5-process DAG to one resident streaming process

The single biggest win is structural, not a kernel trick. The original couples five programs through the filesystem: each stage spawns a fresh python, reloads its models, reads the previous stage's artifacts, and writes its own — including extracting every 4K frame to JPEG so SAM can index a frame directory, and writing every mask as a PNG that ma_2d then re-reads. The port keeps one process alive: a frame is decoded into VRAM once and every stage consumes the same tensor. Disk I/O in the loop: zero (enforced by a test).

2. Decode: NVDEC, decode-ahead, and the torchcodec workaround

Decode runs one chunk ahead of compute on background workers, so wall time approaches max(decode, compute) instead of their sum (critical-path decode cost fell 41 s → 1.1 s). The subtle part: torchcodec 0.10 (conda-forge ceiling) caches a single NVDEC decoder per (codec, resolution), so four identical camera streams in one process evict each other on every chunk. One persistent spawn worker per camera gives each stream its own decoder.

3. Tracking: streaming EfficientTAM + cross-camera batched propagation

The original runs SAM2-hiera-large offline over 4K stills. The port uses the vendored fork's streaming predictor (forward() one frame at a time, bounded forgetful memory bank) with EfficientTAM-ti at 512² — and then removes the last per-camera python loop: because all cameras advance in lockstep, their memory banks always hold the same slot structure, so the per-tick memory-attention → mask-decode → memory-encode pipeline runs once at batch 4 instead of four times at batch 1.

4. Landmarks: MammaNet under TensorRT FP16 + CUDA graph

MammaNet (ViT encoder + decoder producing 512 dense 2D landmarks per person-crop) converts cleanly to a static-shape TensorRT engine. torch.compile was tried first and rejected: inductor's cudagraphs fight the fitter's manually captured graph in the same process (landmarks got 2× slower). TRT avoids that conflict entirely and its launch overhead is then erased by wrapping execute_async_v3 in our own CUDA graph.

5. Fitting: whole-sequence LBFGS → CUDA-graphed sliding window

The original optimizer is inherently offline (LBFGS over every frame simultaneously, 4 stages). The causal replacement keeps an 8-frame window of pose/translation (betas shared and frozen after bootstrap), warm-starts each tick from the previous solution, and runs 16 Adam iterations — where one iteration = forward over an exact 512-vertex SMPL-X (the sampling matrix is folded into the template/shapedirs/LBS weights; max error vs full model 5e-7) + losses + backward + step, captured once as a CUDA graph and replayed. The same trick applied to the 300-iteration bootstrap is what let quality and speed coexist: cutting bootstrap iterations broke the golden gate (38.4 mm), replaying them in a graph kept all 300 at a fifth of the cost.

6. Hiding latency: worker threads + async NVENC logging

Logging is part of the gate, so it had to get cheap too: per-camera 720p frames are converted to YUV420 on the GPU (BT.601, replacing CPU swscale), NVENC-encoded, and logged as per-tick rr.VideoStream samples from a dedicated worker thread. The SMPL-X fit runs one tick deep on its own worker — it feeds nothing upstream, so fit(t) overlaps track/landmarks(t+1).

7. The campaign, end to end

Every bar was gate-verified before moving on; the two rows that traded quality for speed (track stride, fit cadence at high stride on dynamic motion) were later reverted to quality defaults after RRD-level evidence — the shipped configuration is the blue bar, with the fastest verified configuration one flag away.

So EfficientTAM's memory bank starves when the tracker runs every 4th frame: during fast motion the propagated mask keeps only the head until the next good memory refresh (self-recovers within ~0.5–1 s). Decisions & deviations

DEVIATION Vendored sam2 fork is trimmed, not pristine

Removed demo/, notebooks/, sav_dataset/, assets/, training/, tools/, docker files (~65 MB → 720 KB). No Python in sam2/ itself was touched, so "code modifications: none" still holds. Recorded in packages/sam2-streaming/VENDOR.md. Rationale: repo size; those trees are unused by the pipeline.

DECISION Checkpoint keys kept verbatim; optimizer state dropped

The 1.6 GB Lightning ckpt is mostly optimizer state — the state_dict alone is 0.54 GB (weights_only=True fails to unpickle; conversion ran weights_only=False inside the frozen original env, see tools/convert_ckpt.py). Keys keep their original names (backbone.*, decoder.*, mask_downscaling.*) so the ported module mirrors the original attribute names instead of inventing a renaming map. The monorepo never imports pytorch-lightning.

DECISION sam2 fork API notes for M2

SAM2Prompt takes points_coords/points_labels/boxes/masks_logits (not points); box prompts are [N,4] tensors. Counter helpers on the memory bank differ slightly from the research notes (e.g. non_conditional_memories) — check attribute names against the vendored source, not the notes.

TRADEOFF EfficientTAM variants staged but sam2.1_hiera_small is the M2 default

Uploaded efficienttam_{ti,s}.pt as M6 perf levers (the fork's EfficientTAM configs only work via build_sam2_generic*). Starting tracking quality work on sam2.1_hiera_small, which the original ma_masks used, keeps M2 visually comparable to golden masks before any speed-driven swap.

DECISION M6 perf architecture set by these numbers

torchcodec serializes somewhere per-process (~140 cam-fps cap); the hardware does ~4× that. Plan for M6: (1) decode-ahead thread(s) feeding a ring buffer so wall = max(decode, compute) — at 140 cam-fps decode alone is 10.3 s, leaving the whole budget for models running concurrently; (2) if that's not enough, decode worker processes (torch.multiprocessing CUDA IPC) raise the ceiling to ~400 cam-fps. TRADEOFF Per-frame D2H + swscale conversion costs ~4 s

15.4 s total vs 11.4 s decode+D2H: the gap is PyAV rgb24→yuv420p reformat + per-frame copies in the logging path. M6 options: batched D2H per chunk, GPU RGB→YUV before a planar encode_yuv_planes call, encoder threads per camera. Not optimized in M1 by design.

Decisions, deviations, findings

DEVIATION multimask_output=False for all forwards

The fork's forward() defaults to multimask; selecting by predicted-IoU argmax intermittently picked the whole-scene candidate during propagation (observed as full-frame masks). Upstream SAM2 propagates with single-mask output; we now always pass multimask_output=False.

DECISION Bootstrap reference points are box centers, not mask centroids

The original bootstrap used mask centroids as epipolar reference points; at tick 0 we only have detection boxes, so box centers stand in. Same scoring constants (0.35 CLIP + 0.65 epi, min 0.25).

DECISION crossing_arms demo pins expected_subjects=1

Without it, YOLO legitimately finds background crew and a person on a TV screen and tracks them (verified visually — the tracker handled 3 IDs fine). The golden fit is body 00 only, so the pixi demo task passes --tracker.expected-subjects 1. Multi-person stays supported for other datasets.

DECISION Rerun mask logging: full-res SegmentationImage at stride 5 + boxes every tick

Half-res seg images render in their own pixel space under the pinhole (misaligned quadrant), so masks log at full resolution but only every 5th tick to keep the RRD small. Also: an AnnotationContext MUST define id 0 with a transparent color — otherwise the viewer auto-colors the background class and tints the whole frame (cost an hour of debugging; the masks were always correct).

TRADEOFF Tracker cost ~101 ms/tick (4 cams, hiera-small, bf16)

~25 ms/camera-forward sequential. M6 levers: batch the 4 cameras through encode_image as one batch + forward_embeddings per camera, efficienttam_ti, torch.compile, mask-refresh stride. Decode (1.35 s/32-frame chunk) and tracking currently serialize; decode-ahead overlap is the other big lever.
