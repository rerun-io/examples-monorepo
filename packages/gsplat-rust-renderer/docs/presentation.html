Background: what is 3D Gaussian Splatting?

Kerbl et al., SIGGRAPH 2023 — a scene representation made of millions of fuzzy, colored ellipsoids.

The representation

A trained scene is a cloud of anisotropic 3D Gaussians. Each splat carries:

  • center μ ∈ ℝ³ — world position
  • rotation q (quaternion) + scale s ∈ ℝ³ — together they define the covariance Σ = R·diag(s²)·Rᵀ
  • opacity α ∈ [0, 1]
  • color — spherical-harmonic (SH) coefficients up to degree 4, so color shifts with viewing direction (specular-ish effects)

Rendering = project → sort → blend

  • Project each 3D Gaussian to a 2D Gaussian on screen (an ellipse with a 2×2 covariance) using a local linearization of the camera (the Jacobian)
  • Sort splats by depth — alpha blending is order-dependent
  • For each pixel, accumulate α-weighted color front-to-back until the pixel is opaque

There is no triangle geometry and no ray tracing — it is closer to a massively parallel, depth-sorted particle renderer.

What this package does

It implements that renderer twice over a single shared core: once embedded inside the Rerun viewer (interactive), and once as a headless CLI that renders PNGs for quality evaluation. The GPU pipeline is a tile-based compute-shader design (no CUDA — pure wgpu/Vulkan) modeled on Brush, so its output is numerically comparable to a reference implementation.

Cloud building (unpacking arrow arrays, baking the transform, normalizing quats) is the expensive CPU part — for a static scene it happens once, and camera motion costs nothing here.

SH validation (extract_sh_coefficients)

  • Shape must be [N, C, 3] with N == splat count
  • C must map to a degree: {1, 4, 9, 16, 25}
  • dtype must be F32; total length checked with overflow-safe math
  • Any violation is a hard ViewSystemExecutionError — bad data fails loudly, not silently

Building the cloud — build_render_cloud() rust → core

The only place that understands Rerun's query-result format. Everything downstream sees flat arrays.

// range_zip_1x4 walks the 5 component columns in lockstep.
for (_idx, centers, quats, scales, opacities, colors) in
    re_query::range_zip_1x4(centers, quaternions, scales,
                            opacities, colors)
{
    // defensive: min length across all five columns
    let count = centers.len().min(quats.len())
        .min(scales.len()).min(opacities.len()).min(colors.len());

    for row in 0..count {
        // ★ only POSITIONS get the entity transform
        means_world.push(transform.transform_point3(center));
        quats_world.push(normalize_quat_or_identity(q));
        scales_world.push(scale.max(Vec3::splat(1e-6)));
        opacities_world.push(opacity.clamp(0.0, 1.0));
        colors_world.push(rerun_color_to_rgb(color)); // u32→[f32;3]
    }
}

Arc slices: cheap to clone into the renderer each frame; immutable, shared, no copies.

⚠ Why only positions are transformed

Quaternions and scales stay in entity-local space — intentionally, matching Brush. The GPU shader builds the 3D covariance from raw quat + scale, then applies the view matrix inside the Jacobian projection. Baking an arbitrary affine into the covariance would require decomposing rotation from non-uniform scale, which is fragile. Trade-off: non-rigid entity transforms (shear/non-uniform scale) only move centers, not splat shapes.

From the live 3D view (camera_from_spatial_view_state)

  • Rerun stores world_from_rub_view — invert it to get view-from-world

Fallback camera (gsplat_core/camera.rs)

Before the user ever touches the view, last_eye is None. The fallback frames the cloud's bounding box:

  • eye = center + (d, d/2, d) where d = 1.5 × ‖extent‖
  • 55° vertical FOV, 1600×900 viewport, near = 0.01

So splats are visible on first frame — same logic the Python blueprint mirrors with EyeControls3D.

Third constructor: NeRF cameras (camera_from_nerf_transform)

For the standalone path: a 4×4 camera-to-world from transforms_*.json (OpenGL convention, row-major in JSON → transposed) is inverted; vertical FOV is derived from the dataset's horizontal camera_angle_x and the aspect ratio:

fov_y = 2·atan( tan(camera_angle_x / 2) / aspect )

CPU pre-pass: cull + sort gsplat_core/culling.rs

An approximate, conservative first pass. The GPU re-does projection exactly — this pass exists to (a) bound the GPU workload and (b) establish the global depth order that alpha blending requires.

Per-splat rejection test — build_compute_candidate()

  • opacity × OPACITY_SCALE ≤ 0 → reject
  • view-space depth (−z) ≤ near plane or non-finite → reject (behind camera)
  • clip-space w ≈ 0 → reject (degenerate projection)
  • |NDC x| or |NDC y| > 1.5 → reject (generous 50% margin keeps splats whose center is offscreen but whose ellipse still touches the screen)

Survivors become SortedSplatIndex { splat_index: u32, camera_depth: f32 }.

Then two ordering steps

  • Cap to 200 000: select_nth_unstable_by — an O(n) partial sort that keeps the closest splats when over budget (far splats get dropped first)
  • Sort back-to-front (descending depth) — the order alpha compositing needs

Adaptive parallelism

if cloud.len() >= PARALLEL_SPLAT_THRESHOLD { // 16 384

Why sort on the CPU at all?

The GPU radix sort (stage 4) sorts by tile ID only — it's a stable sort, so within each tile, splats keep the order they were submitted in. The CPU's global depth sort is what makes that within-tile order front-to-back. Depth ordering is established once on the CPU; tile grouping happens later on the GPU.

Handoff detail

The visualizer sorts back-to-front, but the renderer uploads the index list reversed (visible.iter().rev()) — the GPU rasterizer blends front-to-back with a transmittance accumulator, which enables early termination per pixel.

The GPU renderer: gaussian_renderer.rs rust gpu

2 545 lines — the biggest file. It implements re_renderer's Renderer trait and owns all GPU resources for the viewer path.

Created once — create_renderer()

  • 13 compute pipelines from 5 WGSL shaders (embedded via include_str! at compile time)
  • 11 compute bind-group layouts + 1 composite layout
  • 1 render pipeline for the composite blit: re_renderer's shared screen-triangle vertex shader + fs_main from gaussian_composite.wgsl, premultiplied-alpha blending, depth-write disabled
  • The composite shader is registered into re_renderer's virtual filesystem (register_embedded_shaders(), once)

Per entity, cached — batch_cache: Mutex<HashMap<String, CachedBatchResources>>

~35 buffers + ~17 bind groups per logged entity, keyed by "gaussian_splats::{entity_path}". Buffers are grow-only (never shrink) so a static scene re-renders with zero allocations — camera movement only rewrites uniforms and the index buffer.

Per-frame: prepare_compute_batch()

1 · Ensure capacity grow instance buffers if visible count > capacity (next power of two, min 1024); rebuild affected bind groups
2 · Poll readbacks async intersection-count readback may demand bigger intersection buffers (slide 21)
3 · Ensure raster target tile_offsets buffer + Rgba8 raster texture sized to ⌈viewport/16⌉ tiles
4 · Write uniforms camera matrices, viewport, SH degree, σ-coverage (f32 bits packed in u32 fields)
5 · Upload indices CPU's back-to-front list, reversed → front-to-back, one write_buffer
6 · Encode compute all 7 stages recorded into re_renderer's before_view_builder_encoder — guaranteed to run before the frame's draw passes
7 · Return batch just the composite bind group; the draw phase needs nothing else

draw() — almost trivial by design

By draw time the image already exists in the raster texture. The draw call is 3 vertices: pass.draw(0..3, 0..1) in the Transparent phase.

Stage 1 — Project gaussian_project.wgsl :: project_main

128 threads per workgroup, one thread per CPU-selected candidate. The exact projection the CPU pass only approximated.

The math, in order

Σworld = R(q) · diag(s²) · R(q)ᵀ 3D covariance from quat + scale
Σview = V · Σworld · Vᵀ V = 3×3 linear part of view matrix
Σpx = J · Σview · Jᵀ J = 2×3 Jacobian of pixel projection at the mean (EWA-style local linearization)
Σ′px = Σpx + 0.3·I anti-aliasing blur (BRUSH_COVARIANCE_BLUR_PX) — no sub-pixel needles
conic = Σ′px⁻¹ inverse 2×2, what the rasterizer evaluates per pixel

The Jacobian rows clamp UVs to 15% beyond the viewport (lims_pos/lims_neg) — splats at screen edges stay numerically sane. Identical Rust reference implementations live in gsplat_core/covariance.rs for testing.

Culling & output (per thread)

  • Cull on GPU: behind near plane · opacity < 1/255 · power threshold ≤ 0 · radius < 0.35 px · ellipse fully offscreen · any non-finite intermediate
  • Power threshold = ln(255·α) — the Mahalanobis level where the splat's contribution drops below 1/255 (invisible at 8-bit)
  • Screen bbox = √(2·threshold·variance) per axis → converted to a tile-space bbox (16-px tiles, with a y-flip: NDC is y-up, the raster texture is y-down)
  • Exact tile test: for each tile in the bbox, will_primitive_contribute() finds the point of maximum Gaussian power inside the tile rect — only genuinely-touched tiles are counted → num_tiles_hit
  • SH color evaluated here if present (next slide)

Spherical harmonics — view-dependent color wgsl sh.rs

Implemented twice with identical constants — WGSL for the GPU and Rust as a tested reference. Same basis ordering as 3DGS, Brush, and gsplat.

How it works

  • View direction = normalize(splat_center − camera_position) in world space
  • Color = Σ basisᵢ(dir) · coeffᵢ over all coefficients, per RGB channel
  • Activation: color = max(raw + 0.5, 0) — the +0.5 bias makes a zero SH field mid-gray instead of black
  • Degree fully unrolled in the shader with early returns — degree-0 scenes pay for one multiply, not 25

Memory layout

Coefficients are stored interleaved: [splat][coeff][rgb], flat Arc<[f32]> on the CPU, padded to vec4f stride on the GPU. The PLY format stores them channel-major (all R, then G, then B) — both loaders re-interleave at load time, and pad with zeros up to the next supported size {1, 4, 9, 16, 25}.

Stage 2 — Prefix sum (“compact”) scan_blocks_main · scan_block_sums_main

Answers one question entirely on the GPU: where does each splat write its tile intersections, and how many are there in total?

Two-level scan

  • Level 1 — scan_blocks_main: 256 threads handle 512 items per block (2 each) in shared memory (scan_scratch). A Hillis–Steele inclusive scan, converted to exclusive by subtracting each item's own value. Writes per-item local_offsets + each block's total into block_offsets.
  • Level 2 — scan_block_sums_main: one single workgroup exclusive-scans the block totals in place (512 blocks × 512 items = 262 144 splats max — comfortably above the 200 k cap).
  • The grand total lands in draw_indirect_args[1] — a DrawIndirectArgs-shaped buffer that stays on the GPU.
global_write_offset(i) = local_offsets[i] + block_offsets[block(i)]

Worked example

tile_hit_counts   = [ 3, 0, 2, 5, 1, ... ]   // from project
                      │  invisible splat: 0 hits
                      ▼  exclusive prefix sum
tile_hit_offsets  = [ 0, 3, 3, 5, 10, ... ]
total (on GPU)    = 11  → draw_indirect_args[1]

Why this is the compaction

Splats culled in stage 1 simply report 0 tile hits, so they occupy zero space in the intersection array — no separate compaction step is needed for the tile path. (The shader still carries a legacy instanced-quad path — scatter_main, an InstanceData output and bindings 32–37 — which the current pipeline never dispatches.)

These same two entry points are reused inside the radix sort (stage 4) to scan digit histograms — one scan implementation, two jobs.

Stage 3 — Map intersections gaussian_map_intersections.wgsl

The “scatter” that turns per-splat tile coverage into a flat, sortable list.

map_main — one thread per splat

  • Re-walks the tile bbox from stage 1, repeating the exact will_primitive_contribute() test (recomputing is cheaper than storing the per-tile mask)
  • For each contributing tile, writes a pair at base + written:
    • tile_id_from_isect[k] = tx + ty·tile_bounds_x — the sort key
    • compact_gid_from_isect[k] = splat_slot — the sort value
  • Every write is bounds-checked against intersection_capacity — dense scenes can overflow the allocation; overflowing pairs are dropped this frame (and the async readback grows the buffer for the next — slide 21)

Example

// splat #42 covers tiles 5, 6, 9, 10 → four entries:
tile_id_from_isect      = [ ...  5,  6,  9, 10 ... ]
compact_gid_from_isect  = [ ... 42, 42, 42, 42 ... ]

clamp_count_main — a one-thread dispatch

num_intersections[0] = min(intersection_count_words[1],
                           map_uniforms.intersection_capacity);

The clamped count is what every later stage (sort, tile offsets, raster) reads as its element count — directly from GPU memory. This is the trick that keeps the whole frame free of CPU↔GPU round-trips.

Stage 4 — GPU radix sort gaussian_dynamic_sort.wgsl

The heaviest machinery in the codebase: a multi-pass, GPU-driven, stable 4-bit LSD radix sort of (tile_id → splat_id) pairs.

One pass = 6 dispatches (repeated per 4-bit digit)

1 · sort_count_main per-workgroup histogram of the current 4-bit digit (16 bins, shared-memory atomics) → counts[bin·num_wgs + wg]
2 · sort_reduce_main tree-reduce histogram chunks → reduced[] partial sums
3+4 · scan_blocks / scan_block_sums exclusive scan of reduced[] — reusing the stage-2 scan entry points
5 · sort_scan_compose + sort_scan_add fold the scanned block offsets back: each workgroup's counts entry becomes a global base offset for its digit
6 · sort_scatter_main per workgroup: loop over the 16 bins, intra-workgroup prefix scan ranks the matching keys, then write key+value to base + rank — order-preserving (stable)

Pass count is data-driven

tile_count_bits = bits_needed(tile_count)
sort_passes     = ceil(tile_count_bits / 4)

1080p → 120×68 = 8 160 tiles → 13 bits → 4 passes (24 dispatches). Only the bits that can actually differ get sorted.

Ping-pong buffers

Even passes: tile_id/gid → sort_keys/alt. Odd passes: back again. If the pass count is odd, a final copy_buffer_to_buffer restores results to the primary pair.

No CPU in the loop

Every entry point starts with let total = num_keys() — read from the GPU buffer stage 3 clamped. Dispatch sizes are based on buffer capacity; surplus workgroups exit immediately.

Why stable matters: keys are tile IDs only — depth is not in the key. Stability preserves the CPU's front-to-back submission order within each tile, which is exactly what the rasterizer's front-to-back blending assumes. (sort_scan_main, a single-workgroup scan variant, is compiled but the shipped path uses the shared two-level scan instead.)

Stage 5 — Tile offsets gaussian_tile_offsets.wgsl

70 lines that convert the sorted list into per-tile ranges. The simplest stage — and the one that makes stage 6 fast.

Boundary detection

  • The tile_offsets buffer (2 × u32 per tile) is cleared to zero first — tiles nothing touches keep {0, 0} = an empty range
  • Each thread inspects 8 consecutive sorted entries (CHECKS_PER_ITER) to amortize dispatch overhead
  • Where tile_id != prev_tile_id: close the previous tile's range and open the new one; entry 0 and entry total−1 handle the ends
if tile_id != prev_tile_id {
    tile_offsets[prev_tile_id * 2u + 1u] = isect_id;  // end
    tile_offsets[tile_id      * 2u     ] = isect_id;  // start
}

Example

sorted_tile_ids = [ 0, 0, 0, 1, 1, 2, 2, 2, 2, 3 ]

tile_offsets[0] = { start: 0, end: 3 }
tile_offsets[1] = { start: 3, end: 5 }
tile_offsets[2] = { start: 5, end: 9 }
tile_offsets[3] = { start: 9, end: 10 }
tile_offsets[7] = { start: 0, end: 0 }   // untouched tile → empty

Why ranges instead of lists

In stage 6, each tile's workgroup reads exactly two u32s and then streams a contiguous slice of the sorted arrays. Contiguity is what makes the shared-memory batching in the rasterizer coalesced and fast.

Stage 6 — Tile rasterization gaussian_raster_tiles.wgsl

Where pixels are actually shaded. One workgroup = 256 threads = one 16×16 tile; one thread = one pixel.

Cooperative inner loop

  • Lane 0 fetches the tile's [start, end) range once into workgroup memory
  • Pixels are mapped within the tile in Morton (Z-curve) order (decode_morton_2d) — neighboring threads shade neighboring pixels, improving memory locality
  • Splats are processed in batches of 256: each thread loads one ProjectedTileSplat into shared memory (local_batch), barrier, then every pixel iterates the whole batch — 256 global reads serve 65 536 pixel-splat evaluations

Per pixel, per splat

σ = ½·(c.x·Δx² + c.z·Δy²) + c.y·Δx·Δy Mahalanobis²/2 via the conic
α = min(0.999, opacity · e−σ)
color += rgb · α · T   ·   T ← T·(1 − α) front-to-back “over”

Early termination — the big win

if transmittance <= 1e-4 { done = true; break; }

Once a pixel is effectively opaque it stops evaluating splats entirely. This is why everything upstream worked so hard to deliver splats front-to-back: in dense scenes most pixels saturate after a handful of splats and skip hundreds more.

Output

textureStore(out_img, pixel,
    vec4f(color_out, 1.0 - transmittance));

RGB is premultiplied; alpha = accumulated coverage. The texture is Rgba8Unorm, sized to whole tiles (⌈w/16⌉·16 × ⌈h/16⌉·16) — edge pixels outside the viewport are computed but masked by the inside flag.

Guard rails

α capped at 0.999 (T never reaches exactly 0 → no NaNs), splats with σ < 0 or α < 1/255 skipped, all threads stay in the batch loop for barriers even when done.

Stage 7 — Composite into the Rerun viewport gaussian_composite.wgsl rust

The only stage that is viewer-specific — it is how a compute-shader image re-enters Rerun's normal render graph.

Fullscreen triangle, no vertex buffer

// vertex: 3 hard-coded positions that cover the screen
var positions = array<vec2f, 3>(
    vec2f(-1.0, -1.0), vec2f(-1.0, 3.0), vec2f(3.0, -1.0));

// fragment: direct unfiltered pixel fetch, clamped to image
let pixel = min(vec2u(in.position.xy), dims - 1);
return textureLoad(raster_color, vec2i(pixel), 0);

One oversized triangle beats two quads — no diagonal seam, fewer helper invocations. textureLoad (not sampled): raster texture and viewport are pixel-aligned, so filtering would only blur.

How it plugs into re_renderer

  • GaussianDrawData::collect_drawables() emits one drawable per entity into the Transparent draw phase
  • The render pipeline blends with PREMULTIPLIED_ALPHA_BLENDING — matching the rasterizer's premultiplied output
  • depth_write_enabled = false: splats composite over already-drawn opaque geometry (point clouds, meshes in the same view) but never occlude it in the depth buffer
  • The whole draw is pass.set_bind_group(...); pass.draw(0..3, 0..1)

Ordering guarantee

The compute work was recorded into before_view_builder_encoder, which re_renderer submits before any view rendering — so by the time the Transparent phase samples the raster texture, the image for this frame is complete. No fences or callbacks needed.

Buffer management & the async readback trick

The renderer can never know in advance how many (tile, splat) pairs a frame will produce — it depends on the camera. The solution: optimistic capacity + a non-blocking feedback loop.

Capacity policy (gpu_types.rs)

ResourceSizing rule
instance / per-splat buffersnext_capacity(n) = next pow-2, min 1024 — grow-only
intersection buffers32 × instance capacity, next pow-2 (INTERSECTION_CAPACITY_MULTIPLIER)
scan block buffers⌈n / 512⌉ blocks, next pow-2
sort histogram buffersderived from intersection capacity / 256-key blocks
tile offsets + raster textureresized when the viewport tile grid changes

Growth rebuilds the affected buffers and all bind groups that reference them (refresh_compute_bind_groups() — bind groups bake buffer handles in wgpu).

Intersection-count readback — a 3-state machine, 2 slots

Frame N — Idle → CopySubmitted copy_buffer_to_buffer: GPU intersection counter → a small MAP_READ staging buffer (16 B)
Frame N+1 — CopySubmitted → Mapping map_async requested; completion flag delivered via Arc<Mutex<Option<bool>>>
Frame N+2 — Mapping → Idle read words[1] (the total). If it exceeds capacity → grow buffers + refresh bind groups for the next frame

The trade

The render path never blocks on the GPU. The cost: when capacity is exceeded, that frame silently drops the overflow intersections (bounds-checked writes in stage 3) and intersection_capacity_saturated is flagged — correct again within ~2 frames. Two slots ping-pong so a copy can be in flight every frame.

Path B — the standalone renderer gsplat-render

Same pipeline, zero Rerun. Exists so rendering quality can be measured headlessly (CI, benchmarks) against reference implementations.

gsplat-render \
  --ply data/trained/chair.ply \
  --camera data/nerf-synthetic/chair/transforms_test.json \
  --frame 0 --width 800 --height 800 \
  --background 1,1,1 \
  --output /tmp/chair_test_0.png     # or: --benchmark

Differences from the viewer path

  • GpuContext (gpu_context.rs): headless wgpu — no window/surface, high-performance adapter, hard-fails if the adapter can't do 11 storage buffers per stage
  • gpu_render() (gpu_renderer.rs, 731 lines): allocates everything per call — no caching, no async readback (it sizes intersection buffers at 32× up front and blocks at the end anyway)
  • No composite: the raster texture is copied to a staging buffer (rows padded to wgpu's 256-byte alignment), mapped with pollster, and converted to RGB8 over the background color (RenderOutput::to_rgb8)
  • Cameras from disk: nerf_camera.rs parses transforms_*.json; ply_loader.rs mirrors the Python PLY parsing field-for-field

Version pins that matter

rerun = "=0.31.1" (and all 13 re_* crates) and wgpu = "=29.0.1" are pinned exactly — the renderer reaches into re_renderer internals (encoders, shader FS, draw phases) and shares its wgpu device, so ABI/API drift would break the build or worse, the frame.

Design decisions worth stealing (and quirks worth knowing)

✅ Single source of truth for GPU plumbing

Bind-group layouts, pipeline creation, buffer structs, packing and dispatch math all live once in gpu_types.rs. The two paths can't drift apart — a layout change breaks both or neither. A Rust unit test even asserts TileProjectedSplat's field offsets match the WGSL stride.

✅ Rerun-free core = testable core

CPU reference implementations (covariance, SH, culling) mirror the WGSL and are unit-tested without a GPU or a viewer. The standalone binary turns the whole pipeline into a measurable function: (PLY, camera) → PNG → PSNR.

✅ The frame never blocks on the GPU

Counts that later stages need are produced, clamped, and consumed on the GPU; the only readback is async with 2-frame latency and only tunes capacity. Worst case under growth: a frame drops some far intersections, never a stall.

⚠ Hybrid CPU/GPU sorting

Depth order comes from the CPU (global sort, capped at 200 k); the GPU only groups by tile (stable radix). Cost: large clouds re-sort on the CPU when the camera moves. Brush sorts depth on the GPU too — this design trades that for simplicity and gets away with it under the 200 k cap.

⚠ Legacy remnants of an instanced-quad path

InstanceData outputs (binding 6), visibility_flags, and scatter_main are still written/compiled but never consumed by the tile path. They're kept as documented lifetime anchors / compat — useful to know before “cleaning up” bindings.

⚠ Coordinate flips live in exactly one place

NDC is y-up; the raster texture is y-down. Stage 1 flips once (mean_px_raster = (x, h − y)) and everything downstream is consistently raster-space. Quaternion order differs per format too: PLY stores wxyz, everything internal is xyzw.

The one-sentence summary

A Python client streams Gaussian clouds over gRPC into a barely-modified Rerun viewer, where a cached visualizer culls and depth-sorts on the CPU, and a Brush-style 7-stage wgpu compute pipeline — shared verbatim with a headless evaluation CLI — projects, tile-sorts, and alpha-blends them into the viewport at interactive rates.
