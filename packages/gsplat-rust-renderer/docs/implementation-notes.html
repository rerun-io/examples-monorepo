2026-06-10

decisionCalibration scene: an analytic camera test, not just PSNR on real scenes

PSNR on chair/hotdog/ship can mask convention bugs (a small FOV error or sub-pixel principal-point shift just looks like mild blur in the metric). So before trusting the scene comparison, all renderers must pass a calibration scene: a programmatically generated 3DGS PLY containing small isotropic splats at exactly known world positions — origin (white), +X (red), +Y (green), +Z (blue), four corner markers, and one overlapping front/back pair as a depth-order probe. A synthesized transforms_test.json places a camera at a known c2w. For each renderer we detect blob centroids by color mask and compare against the analytically predicted pixel coordinates (pinhole model). This verifies, per renderer: handedness (red on the correct side), the y-flip (blue up), focal/FOV (inter-blob pixel distances), centering, and depth ordering — each failure mode maps to a distinct, diagnosable error.

Writing the PLY requires the inverse activations (scales → log, opacity → logit, color → (rgb − 0.5)/SH_C0 as f_dc), since every loader applies the forward ones.

2026-06-10

decisionViewer FOV: measure it empirically, then match the reference render to it

The viewer's orbit eye has its own vertical FOV which blueprints (as far as known) cannot set. Rather than compare viewer screenshots against mismatched-FOV references, we point the viewer at the calibration scene from a known blueprint pose, measure inter-blob pixel distances in the screenshot, and solve for the effective fov_y (centered-pp pinhole). Then we synthesize a camera_angle_x for gsplat-render that reproduces that FOV at the screenshot's viewport aspect, and render the matched reference. This turns the loose "structural comparison" into a tight one, with the viewer's intrinsics determined by observation instead of assumption.

2026-06-10

decisionExplicit world axes in the viewer: log ViewCoordinates.RIGHT_HAND_Z_UP

NeRF-synthetic worlds are Z-up; the existing log_gaussian_ply.py blueprint used eye_up=(0,1,0) (Y-up), which is wrong for these scenes (works visually only because orbit cameras forgive it). For validation we log rr.ViewCoordinates.RIGHT_HAND_Z_UP at the view origin and set eye_up from the actual camera c2w up-column for matched poses (and to world +Z for orbits). Candidate upstream fix for the tool itself — flagged as a deviation to confirm.

Design decisions

2026-06-10

decisionThree-loop validation strategy

Correctness is established with three nested loops, strongest first:

  • Loop 1 — pixel-exact offline: gsplat-render vs latest-Brush headless renders of the same PLY + same NeRF test camera + same 800×800 + white background. Both consume identical inputs, so PSNR/SSIM between the two images measures implementation divergence directly, independent of scene quality. Diff heatmaps localize disagreement (edges → sorting/AA; tint → SH; silhouette → culling).
  • Loop 2 — ground-truth anchor: both renderers vs the dataset's real test photographs. Catches "both wrong the same way" and yields absolute PSNR comparable to published Brush numbers.
  • Loop 3 — interactive viewer: the actual gsplat-rust-renderer viewer driven over gRPC: blueprints with EyeControls3D placed at the exact NeRF test-camera poses (converted from c2w) plus a 12-step orbit; frames captured from the X display. This exercises everything the CLI path does not: gRPC ingest → archetype query → visualizer cloud cache → view-state camera extraction → full GPU pipeline → viewport composite.

Why: the user's requirement is "close the loop so the hotdog/ship/chair splats correctly look like what they do in Brush." Loop 1 is the only place a pixel-exact claim is possible; loop 3 is the only place the shipped viewer is proven, and the two share loop-2's data so results triangulate.

2026-06-10

decisionData sourcing: pre-trained PLYs from the HF mirror, not retraining

pablovela5620/nerf-synthetic-mirror already hosts trained/{chair,hotdog,ship}.ply (Brush-trained, 30K steps — same provenance as the package's baseline metrics). Using them keeps the comparison about rendering, not training noise, and saves ~30–60 min of GPU training. Scene downloads (transforms_test.json + GT images) come from the same mirror via the existing pixi tasks.

2026-06-10

decisionBrush reference = its own loaders + its own renderer at HEAD

The Brush-side reference images are produced inside a fresh clone of Brush main (in /tmp/brush), using Brush's own NeRF-synthetic camera parsing and its own render kernels — not our reimplementation of either. If Brush lacks a ready-made "render PLY at camera → PNG" CLI, a minimal harness binary is added inside the Brush workspace calling its public crates, so every pixel of the reference comes from Brush code. The exact commit hash is recorded in the report.

2026-06-10

decisionViewer screenshots via X display capture, driven by blueprints

The validation skill's native headless screenshots (ViewerClient.spawn(headless=True)) target the stock Rerun 0.33 viewer; our custom viewer pins re_* = 0.31.1 and does not answer that protocol. Until an upgrade lands (see open questions), viewer evidence is captured by launching the real viewer binary on the machine's X display (hardware Vulkan on the RTX 5090) and grabbing the window with xwd, while the camera is moved declaratively by re-sending blueprints with new EyeControls3D poses. No synthetic input events, no flaky window automation — the blueprint is the camera API.

Phase-1 findings that shape the work

2026-06-10

decisionBrush adoption list: recommend now, port separately — except the 0.33 upgrade

The Brush research produced a ranked porting list. This workflow's scope is: validate the renderer as it stands, perform the (user-approved) 0.33 upgrade, and deliver the recommendations — not port Brush kernels mid-validation (changing the renderer while measuring it would invalidate the comparison). Ranked recommendations (full detail in the final report):

  • ① GPU depth sort (large): Brush culls + depth-sorts entirely on GPU — atomic compaction in the project kernel, then 32-bit radix-argsort over raw f32 depth bits (valid since positive floats sort as unsigned ints). Our CPU pre-sort + 200k cap is our deviation from Brush, and removing it is the strongest answer to the GPU-only directive. Prefer Brush v0.3.0's indirect-dispatch variant (count never leaves the GPU) over HEAD's synchronous readback.
  • ② Subgroup radix sort (medium, ~50% faster sort / 10–15% faster frame, #386) — lift WGSL verbatim from commit d0eaca6f; needs wgpu Features::SUBGROUP.
  • ③ Rasterizer cooperative early-exit (small, #394): workgroup-shared num_done atomic lets a whole 16×16 tile stop streaming batches once every pixel saturates; we only have per-pixel done flags today. ~20 lines.
  • ④ Intersection-buffer hardening (small, #411/#373/#459): one shared contribute-test loop body for count+write passes, min(counted, budget) write gate, sentinel tile-id padding, gated tile-offset writes.
  • ⑤ Mip-Splatting mode (small, #337): blur 0.1 + opacity ×= √(det_raw/det_blur), per-PLY metadata — without it, mip-trained PLYs render over-opaque. Default mode is byte-identical to our current constants.
  • ⑥ Numerical guards (small): 1e18 PSD-preserving covariance clamp, SH color NaN-scrub + [−100,100] clamp, positively-phrased finite checks.
  • Do NOT port: CubeCL (we stay raw WGSL — d0eaca6f is the last full-WGSL Brush tree and our porting source) and HEAD's synchronous count readback (a per-frame GPU→CPU stall; our async 2-frame readback + GPU clamp mirrors v0.3.0's design and respects the GPU-only constraint).
2026-06-10

decisionPhase-2 verdict: camera & viewer proven; ship divergence confirmed and bounded

What is proven correct: calibration geometry ≤ 0.21 px on 9/9 color-resolvable markers for BOTH renderers, depth probe correct (occluded marker invisible) — the camera contract holds end-to-end. The 0.33 viewer answers native headless screenshots (45/45; X11 fallback never needed); measured interactive-eye fov_y = 55.216° (Rerun's default 55°, EyeControls3D exposes no FOV field at 0.33); with measured-FOV compensation, viewer-vs-CLI chair f0 agrees at SSIM 0.9946 — the viewer pipeline renders what the CLI renders. All .rrd files verify clean and survive save→reload→screenshot round-trips.

What diverges: ours-vs-Brush PSNR: chair 33.5 dB / hotdog 28.2 / ship 19.6 (worst: ship f100 close-up, 15.9). Diff maps show one consistent signature: a feathered low-opacity halo past object silhouettes in ours where Brush clips crisply; ours-vs-GT (25.0 global) trails Brush-vs-GT (30.9) by the same mechanism. Reading-level suspects eliminated one by one: mip render mode (PLYs resolve to Default in Brush — comment-driven, none present), bbox-extent formula (Brush's conic form is algebraically identical to our covariance form), #448 smooth alpha cutoff (smoothstep band ±0.0005 around 1/255 — orders of magnitude too small), per-pixel cutoff math (provably equivalent: α ≥ 1/255 ⟺ σ ≤ ln(255α)). Remaining testable asymmetries that can produce one-sided extra coverage in ours: Brush culls degenerate quaternions (we render them as identity), our MIN_RADIUS_PX=0.35 + CPU |NDC|>1.5 center-cull differ from Brush's extent-aware on-screen test, possible count/write drift in the per-tile contribution test (the #411 class), and Brush's inference-branch selection in the rasterizer. Phase 3 settles it with single-variable ablations (each: edit → ~30 s rebuild → 4 renders → PSNR delta → revert).

2026-06-10

decisionPhase-4: the GPU-only port — design, two surprises, and honest throughput

Design (Brush model, our plumbing): project_forward_main culls over the full cloud (extent-aware on-screen test replaces the old CPU center-cull) and atomically compacts (gid, depth); a 32-bit radix argsort over f32 depth bits (ascending ⇒ front-to-back directly) reuses our existing sort machinery — which already reads counts from GPU buffers with capacity dispatches, so the whole thing needs no readback and no indirect dispatch; project_visible_main shades in sorted compact order; everything downstream unchanged. Brush #394 raster early-exit + deferred color reads also applied (bit-identical output, kept).

Surprise 1 — we fixed a nondeterminism Brush itself has: atomicAdd compaction makes depth-tie order race-dependent (~30 f32 depth-bit collisions in chair caused run-to-run pixel flips). An extra gid-canonicalization sort stage makes the stable depth sort resolve ties deterministically — renders are now bit-identical across runs. Surprise 2: the two-level prefix scan silently capped at 262,144 elements — exactly the envelope the old 200k cap guaranteed. A third scan level (reusing existing entry points) was required to make cap removal actually safe.

Throughput (50-frame mean, RTX 5090, before → after → Brush): chair 800² 5.9→4.7 ms (Brush 1.85), chair 1600² 10.1→9.0 (2.82), hotdog 800² 4.0→3.9 (1.85), ship 800² 4.2→4.1 (1.89), ship 1600² 8.7→8.3 (3.30). Faster in all cells; the big win is structural: 309,888 splats render correctly at 31.9 ms where the old CPU path silently truncated to 200k. Honest caveat: our CLI bench re-allocates every GPU buffer and re-uploads all splat data per frame and ends with a blocking full-frame readback (the standalone path's design) — the remaining 2.1–3.2× vs Brush is substantially harness overhead plus the unported #386 subgroup sort; the viewer path reuses persistent buffers.

Deviations

2026-06-10

deviationHeadless mode: vendoring Rerun's headless loop instead of calling run_headless_app

0.33's re_viewer::run_headless_app would give us native headless screenshots "for free" — but it hardcodes a crate-private wgpu config whose device requests zero compute/storage limits (downlevel-WebGL2 defaults, Features::empty()), on which our 7-stage compute pipeline cannot even be created (evidence: re_viewer/src/headless.rs:33, re_renderer/src/device_caps.rs:275-291). So we vendor its ~150-line egui_kittest loop with our full-adapter-limits WgpuSetup. Screenshots still exercise the real Vulkan pipeline on the 5090 — the GPU-only property is preserved; we just had to own the loop. Flagging because it's copied-then-modified upstream code that must be revisited on future Rerun upgrades (the extend-ui docs explicitly warn these interfaces break every release).

2026-06-10

deviationBrush HEAD's dataset loader can't read vanilla NeRF-synthetic JSONs — harness stages a fixed copy

Found while building the reference harness: Brush HEAD checks image existence before appending the default .png extension, and its VFS only indexes files with extensions — so vanilla "file_path": "./test/r_0" entries are all silently skipped (likely an upstream bug worth reporting). The harness stages a copy of the dataset dir with extensions appended in the JSON; camera parsing itself is untouched Brush code. Also: Brush's loader only exposes frames whose GT image file exists on disk — our render matrix uses scene dirs with all 200 test images, and the calibration scene gets a dummy 800×800 GT image so its frame is loadable (Brush derives intrinsics from GT image dimensions, so the dummy must be exactly 800×800).

Tradeoffs

2026-06-10

tradeoffMatched-pose viewer comparison is structural, not pixel-exact

The viewer's interactive eye has its own vertical FOV and the window has UI chrome and a different aspect ratio than the 800×800 dataset cameras, so loop-3 screenshots cannot be compared to loop-1 renders pixel-for-pixel. Choice: place the eye at the exact c2w pose, crop the 3D viewport, and compare structurally (silhouette coverage, color histograms, downscaled SSIM with a loose threshold) + side-by-side panels for human inspection. Alternative considered: synthesizing a CLI camera whose FOV matches the viewer's eye to force alignment — kept as a stretch goal; rejected as the primary method because the viewer FOV is not explicitly published by the view state in 0.31.

2026-06-10

tradeoffFresh worktree builds instead of reusing main-checkout artifacts

The git worktree has its own target/; the main checkout's is empty anyway. Building both binaries fresh costs one long compile (the viewer compiles Rerun 0.31 from source) but guarantees the binaries match the worktree's code exactly. Cargo's 10-minute shell timeout is handled by simply re-running the build command — cargo resumes incrementally.

2026-06-10

decisionHotdog and ship are the priority scenes; "as close as possible" is the bar

User directive: chair alone is not enough — hotdog and ship historically cause more problems (heavy view-dependent SH on the water/specular highlights, thin rigging, many small splats), and the goal is to be as close to Brush as possible, not merely "PSNR looks fine." Consequences: (1) the matrix weights all three scenes equally (8 views each) but divergence analysis leads with hotdog/ship; (2) if ours-vs-Brush on hotdog/ship lands materially below chair, a phase-3 divergence hunt follows — bisecting candidate causes (SH evaluation, AA blur ↔ opacity-threshold interplay, tile contribution test, CPU-cull margins clipping off-center splats, sort tie-breaking) with single-variable ablation renders rather than guesswork.

One suspect already ruled out: all three trained PLY headers carry comment Exported from Brush / SH degree: 3 and no mip render-mode metadata — so Brush HEAD renders them in Default mode (blur 0.3, compensation 1.0), byte-identical constants to ours. Two observations recorded while checking: the headers list f_rest_* properties in alphabetical order (f_rest_0, f_rest_1, f_rest_10…) — harmless since both our loaders read fields by name, but any loader assuming numeric order would silently scramble SH; and Brush writes comment Vertical axis: y although the NeRF-synthetic world is Z-up — metadata-only (renders agree with dataset cameras), worth knowing if a future viewer honors it.

2026-06-10

deviationTHE BUG (fixed): view-space covariance used OpenGL z-sign with a z-forward Jacobian

project_main builds mean_camera = (x, y, −z) (z-forward, positive depth) for the Brush-style Jacobian, but fed it a view-space covariance computed with the raw OpenGL view rotation (camera looks down −z). The frame change is diag(1,1,−1): only the cross-terms σxz/σyz flip sign — so isotropic and screen-parallel splats render identically (chair nearly fine, calibration markers exactly fine), while grazing-angle anisotropic needles (ship's water, anisotropy p99 ≈ 226k) get a wrong 2D shear that grows with (f/z)²·|u,v| — the peripheral wedges and feathered halos. Found by pixel forensics (fur-mask connected-components ruled out tile-blocks/population explanations; streak orientation rotated with azimuth and grew toward the periphery) and proven by a numpy re-implementation of the shader math: buggy convention reproduces our background coverage at r=0.9951; corrected convention matches Brush's. Fix kept (negate the z lane of view_linear's columns, mirrored in the covariance.rs reference): ship f100 15.87 → 59.15 dB, global ours-vs-Brush 27.11 → 61.68 dB, ours-vs-GT == Brush-vs-GT to 0.01 dB on every view. Control experiments E2 (MIN_RADIUS→0) and E3 (CPU cull margin→50) were exact no-ops, confirming the single root cause.

2026-06-10

tradeoffLesson: the calibration scene was blind to exactly this bug class

The calibration markers are isotropic, so σxz/σyz = 0 in view space and the sign bug was invisible to the 0.21 px marker checks — geometry passed while shape was wrong. The scene verifies position (handedness, y-flip, FOV, depth order) but not covariance projection. Improvement queued: add 2-3 highly anisotropic needle markers at oblique orientations near the image periphery, plus an expected-ellipse-orientation check. Also noted: brush_covariance_in_pixels in covariance.rs has no render-path callers and no unit test pinning it to the shader — a golden test comparing the Rust reference against shader output on a needle splat would have caught this at build time.

2026-06-10

deviationThree documented deviations from Brush in the GPU port

(1) gid-canonicalization sort before the depth sort — Brush doesn't have it and is consequently nondeterministic on depth-bit ties; we chose determinism (bit-identical renders) at the cost of extra sort passes. (2) near-plane cull uses camera.near_plane instead of Brush's hard-coded 0.01 (keeps our pre-existing camera contract). (3) capacity dispatch + GPU-buffer counts instead of Brush v0.3.0's indirect dispatch — same GPU-only property, less machinery, consistent with how our tile sort already worked.

2026-06-10

decisionSubgroup sort / E3 / E4: deliberately NOT ported — the speed gate is already exceeded

The perf roadmap (subgroup radix sort #386, scan-based gid compaction E3, indirect tile-sort dispatch E4) was ranked to close a 2.2× throughput gap to Brush. After E5 + R1/R2/E1 the gap is closed with margin — ours is 1.16–1.54× faster than Brush in all six bench cells. The remaining items would now trade away properties the project values more than unneeded speed: the subgroup sort changes float op ordering (forfeits bit-identical renders — the 98% accuracy headroom existed precisely for this, but spending it for nothing is strictly worse), and E3/E4 add kernels/complexity (LOC up, against the 10% reduction goal) for ~0.2–0.6 ms we don't need. They remain documented as future work in brush-comparison.html §7 if a heavier workload (e.g. multi-million-splat scenes at 4K) ever reopens the gap.
