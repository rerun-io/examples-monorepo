Consolidating the CV monorepo into one consistent framework

You don't need to invent the framework — two packages already prove it. monoprior shows the model-wrapper pattern (ABC + factory + typed result), and simplecv is already the shared foundation almost every package imports. The work is naming the pattern, lifting shared types into the foundation, and bringing the other ~15 packages onto the same contract.

00The thesis in three claims

already true

simplecv is the de-facto foundation. 13 of 15 first-party app packages import it for camera parameters, pose conventions, Rerun logging (RerunTyroConfig, log_pinhole, log_video), video IO, triangulation, TSDF fusion, and skeleton definitions. It is the foundation in fact — it just isn't declared as one or scoped deliberately.

already proven

monoprior is the reference pattern. Its models/<task>/ layout pairs a Base<Task>Predictor(ABC) with a get_<task>_predictor(name) factory and a jaxtyping-annotated result dataclass (RelativeDepthPrediction). Every other model package reinvents a weaker version of this. Standardize on it.

the actual work

Group by capability, not by paper. Five human-pose packages all do image → detections → keypoints/mesh but share no types. Four SLAM/VO/SfM packages all do frames → trajectory + map. Collapse these into capability packages over a shared foundation, with one inference contract.

02What's already shared (lean into it)

These conventions already span the repo. They are the seams the consolidated framework should be built along — not things to invent.

simplecv as substrate

imported by 13/15 app packages
  • camera_parameters — Intrinsics, Extrinsics, Pinhole, Fisheye62
  • ops.conventions — convert_pose, camera conventions
  • camera_orient_utils — gravity align / center
  • ops — triangulate, TSDF fuser, pc_utils
  • data.skeleton — mediapipe, COCO-133

Rerun is the universal output

every single package logs to Rerun
  • RerunTyroConfig — the shared CLI/viewer config, embedded in almost every *Config
  • log_video, log_pinhole — common loggers
  • rerun_custom_types — Points2D/3DWithConfidence
  • Output is "log to Rerun / write .rrd", not "return arrays" — for most packages

tyro + config dataclass

the universal CLI mechanism
  • Every demo is tyro.cli(SomeConfig) → main(config)
  • Configs are dataclasses embedding rr_config: RerunTyroConfig
  • Per-package PACKAGE_DIR + pixi tasks with depends-on download chains
  • jaxtyping + beartype (dev) on array shapes everywhere
Implication: the foundation already exists and the I/O boundary is already uniform (config in, Rerun out). The inconsistency is concentrated in one layer — how a model is wrapped and invoked — and in directory naming. That's a narrow, tractable surface to standardize.

04Proposed taxonomy — capabilities are task primitives

Group not by domain (the old "human" bucket) and not by paper, but by task primitive — the output contract. That's what makes detection first-class: DETR, YOLOX, WiLoR's hand detector and RTMDet all map image → Detections, and every top-down pose pipeline consumes them. A capability is one output type behind one factory; anything shaped like detect→crop→estimate is a composition, so it lives in the app tier (§05).

The insight your question surfaces: "human perception" was never a capability — it was three primitives in a trenchcoat: detection (person/hand boxes), keypoints (2D/3D pose), and body-mesh (parametric body), plus the apps that chain them. Detection is the primitive every top-down pipeline shares; promoting it to its own capability gives DETR / YOLOX / YOLO-hand / RTMDet one home and lets hand-pose and body-pose reuse it. The detect→crop→estimate chain is literally a pipeline — which is exactly why it belongs at the app tier, not buried inside one package.

Why detection & instance-seg are one capability (your RF-DETR point): a mask is just a finer-grained detection — its box is the mask's bounding rect. RF-DETR-Seg, Mask R-CNN, YOLO-seg and SAM3 all emit boxes and masks from a single model, so splitting them would force one backend to register twice. Keep them unified behind Detections{… masks?} — box-only detectors leave masks=None; instance segmenters fill it. The genuinely separate contract is semantic segmentation (image → SegmentationMap[h w] of class-ids, no instances) — none in the repo yet; make it its own capability if it appears. Pure interactive SAM (point/box prompt → one mask, no labels) is a different input contract too, but SAM3's text-prompted labeled instances fit the unified type.

05Monorepo layout — foundation · capabilities · apps

You already have packages/simplecv as the foundation; the open question is where the nodes and the compositions live. Three tiers, dependencies pointing strictly down. The pivotal insight you flagged: an app like the multiview calibrator spans several capability packages, so by the no-sibling-imports rule it cannot live inside one — it becomes its own app package. That's what defines the app tier.

app packagesnode compositions

Compositions of nodes from one or more capability packages — e.g. the multiview calibrator (VGGT + SAM3 + MoGe → align → fuse). The only tier allowed to import several capabilities, and it holds no models of its own — just an in-process pipeline (api/), a Gradio UI, and optionally a daggr graph (tools/graphs/).

Single-capability demos stay in that capability's tools/{demos,apps}/; only cross-capability apps get promoted to packages. mv-api and vistadream are already app packages in disguise.

capability pkgsthe models

detection+seg · keypoints · depth · body-mesh · multiview · slam · reconstruction (§04). Each exposes a factory + ABC + typed results. May depend on foundation only — never on each other (compose at the app layer).

Pattern source of truth: monoprior/models/<task>/

foundationsimplecv + kornia

Two pieces: kornia for GPU/differentiable geometry primitives, and simplecv for everything kornia doesn't do — Rerun logging/types, video IO, dataset loaders, skeletons, N-view triangulation, gravity-align, TSDF, plus the base ABCs + result types + registry helper. Depends on nothing first-party. This is the "make everything PyTorch-based" anchor — refined in §06.

Promote shared abstractions here (§08). Today simplecv also holds dataset loaders + a large apis/ — decide whether those split out (§13).

Pixi treats these paths cosmetically — each package is still its own feature + environment — so the subdirectories cost nothing and make the tier (and the legal dependency direction) visible at a glance. If you'd rather stay flat (packages/<name>), keep the tiers as a naming / docs convention instead; the dependency rule is what matters, not the nesting.

The one rule that keeps it clean: dependencies only point down — apps → capabilities → foundation → kornia. Capability packages never import each other; the foundation imports nothing first-party. Cross-capability work doesn't bend this rule, it defines the app tier: the multiview calibrator imports multiview + detection + depth and wires them in-process (§11). mv-api and vistadream already work this way — formalizing the tier just gives them a home and a name.

06Foundation stack — kornia for geometry, simplecv for the rest

"simplecv is NumPy-based" conflates two different things, and only one is a throughput problem. The fix isn't migrating simplecv to torch — it's depending on kornia for GPU geometry, keeping simplecv for everything kornia doesn't do, and making torch tensors (not NumPy) the type that flows through the predictor contract.

Reframe: NumPy is only slow for heavy per-pixel data — images, depth maps, heatmaps, masks — where it forces host↔GPU round-trips. For tiny metadata — a 3×3 K, a pose, a voxel size — device location is irrelevant; keeping those as jaxtyping dataclasses is fine. The throughput fix is narrow: keep heavy tensors on-device through the predictors, not "torch-ify all of simplecv."

Three options, one answer

Emulate kornia skip

Rebuilding batched, differentiable geometry shadows an 11k-star, Apache-2.0 library that's been at it since 2018 — and you'd stay permanently behind. Pure cost, no upside.

Migrate all of simplecv skip

~70% of simplecv is out of kornia's scope — logging, IO, loaders, skeletons, TSDF, N-view triangulation. Torch-ifying a dataset loader or a Rerun logger buys nothing.

Depend on kornia adopt

Delete simplecv's overlapping geometry internals; have its ops call kornia under the hood. Batched, on-device, autograd geometry for free; keep your typed API on top.

The boundary rule: heavy tensors stay torch on-device from model input through every predictor and result type; collapse to NumPy only at the Rerun logging edge — which wants CPU/NumPy anyway. And wrap kornia, don't expose it: your public API stays jaxtyping + dataclasses, kornia is an implementation detail behind it — so beartype/jaxtyping discipline is preserved (kornia documents shapes in docstrings only).

Caveats to plan around

  • conda-forge trails PyPI by ~1 release (0.8.2 vs 0.8.3). Pin via conda-forge, or use pixi pypi-dependencies if you need the latest.
  • kornia_rs image IO is Linux-only. Non-issue here, and you already have your own video IO — you don't need kornia.io.
  • N-view triangulation and gravity-align stay yours forever — kornia won't fill those two gaps.
  • Style mismatch is real: kornia is plain-tensor + nn.Module + docstring shapes. Wrapping it is what keeps your dataclass / jaxtyping API intact.

07The unified inference contract

Generalize monoprior's existing pattern verbatim. Three pieces per task: a result dataclass, a base predictor ABC, and a string-keyed factory. This is what makes models swappable and lets one viewer/benchmark/UI take "any depth model" or "any pose model."

The pattern monoprior already ships

# monoprior/models/relative_depth/__init__.py  — this already exists
RELATIVE_PREDICTORS = Literal[
    "DepthAnythingV2Predictor", "MogeV1Predictor", "UniDepthRelativePredictor", ...
]

def get_relative_predictor(name: RELATIVE_PREDICTORS) -> Callable[..., BaseRelativePredictor]:
    match name:
        case "MogeV1Predictor": return MogeV1Predictor
        ...

Generalized as a foundation contract (one per capability)

# simplecv/inference/base.py  — promote the shape, keep it tiny
@dataclass
class DepthMap:                          # result types are jaxtyping dataclasses
    depth: Float32[np.ndarray, "h w"]
    confidence: Float32[np.ndarray, "h w"]
    K_33: Float32[np.ndarray, "3 3"]

class BasePredictor[InputT, ResultT](ABC):   # the universal model wrapper
    @abstractmethod
    def __call__(self, x: InputT) -> ResultT: ...
    def set_model_device(self, device: Device = "cuda") -> None: self.model.to(device)

# each capability package then declares its own Literal + factory:
#   get_depth_predictor(name)  -> BasePredictor[Image, DepthMap]
#   get_pose_predictor(name)   -> BasePredictor[Image, Keypoints2D]
#   get_segmentor(name)        -> BasePredictor[ImageAndPrompt, Masks]

And a Pipeline contract for streaming/multi-frame work

SLAM/VO/SfM and video predictors aren't single-shot — keep dpvo & mast3r-slam's existing good idea (a generator that yields progress + a mutable Handle) but name it once:

class BasePipeline[ConfigT, ResultT](ABC):
    def run(self, cfg: ConfigT) -> Generator[Progress, None, ResultT]: ...
# SlamPipelineHandle / DPVOPrediction already match this shape — just unify the names.
Vocabulary to settle (you flagged this): Predictor = single-shot model wrapper (__call__(input) → Result). Pipeline = orchestrates predictors + IO over a stream/dataset (run(config) → Result, may yield progress). App = a Gradio UI. Demo = a tyro CLI. Pick these four words and ban the synonyms (Estimator, Tracker, Runner, Node, *3dEstimationPipeline) — or remap them deliberately.

09The one package anatomy

After settling the naming forks (§03), every capability package looks identical — and each is a self-contained, composable unit. The rule that makes it modular and fast: a predictor is a DAG node, compositions run in-process, and nothing in src/ imports an orchestrator (§11).

packages/<capability>/
  pyproject.toml              # [project] + build + [tool.ruff] only (pixi config stays in root)
  src/<module>/               # src-layout everywhere (§13)
    __init__.py               # beartype activation (PIXI_DEV_MODE)
    models/                   # ← swappable core; the ONLY place weights/forward live
      <task>/
        base.py               # Base<Task>Predictor(ABC) + result dataclass (batch-first §08)
        __init__.py           # Literal of names + get_<task>_predictor() factory (§07)
        <backend>.py          # one file per model backend
        conversion/           # torch → ONNX → TRT export + engine build (§10 · Decision 3)
    api/                      # config-driven orchestration + in-process DAG pipelines (§07 · §11)
    gradio_ui/                # Gradio blocks — one per predictor / pipeline
  tools/
    demos/                    # tyro CLI entrypoints (headless)
    apps/                     # gradio launchers — what daggr GradioNodes point at
    graphs/                   # daggr graph defs — OPTIONAL, app tier, never imported by src/
  tests/

# deps:  simplecv (foundation) + kornia (geometry).  NEVER another capability pkg.  NEVER daggr.
Why this shape: models/ is the swappable core — each predictor is a typed DAG node (factory + ABC + batch-first result, §07). api/ composes nodes in-process into pipelines (tensors stay on the GPU between stages, §11). gradio_ui/ + tools/ are disposable presentation. Two rules keep it modular without lock-in: a package depends only on the foundation + kornia (cross-capability work composes at the app tier, never by importing a sibling), and nothing in src/ imports daggr — orchestrators consume the package, not the reverse.

10The image boundary — format, loading & batching

Three questions decide throughput: what format crosses the boundary, how frames get there, and whether everything is batch-first. The table is the ground truth from each model's preprocessing — the tensor that actually hits forward() after every cvtColor/permute/normalize. The decisions under it settle one canonical boundary, one loader, and one batching rule. The recurring theme: the foundation fights itself — IO hands out BGR-on-CPU-NumPy while models want RGB-on-GPU-tensor, and torchcodec is already a dependency wired to throw its own advantages away.

Color = what the network consumes after any internal flip (e.g. WiLoR & Sapiens2-torch take RGB at the API but flip to BGR before forward). "internal" = preprocessing fully delegated to a vendored lib (transformers / ultralytics / rtmlib) so the wrapper hands it an HWC uint8 array. classical backends (pycolmap in pysfm, cuVSLAM in robocap) are omitted — no neural-net image input.

⚠ The foundation contradicts itself today. simplecv's image types are BGR (ImageBGR, BGRList), and every reader — including all three TorchCodec* variants — hardcodes device="cpu", dimension_order="NHWC", and cv2.cvtColor(RGB→BGR) to stay OpenCV-compatible (video_io.py). So torchcodec decodes RGB, the wrapper flips it to BGR on the CPU as NumPy, and most predictors then flip it back to RGB and copy it to the GPU. Two needless conversions and a host→device copy per frame — exactly the cost you want to remove.

Decision 1 — canonical format RGB · uint8 · NCHW · on-device

  • Color = RGB — the ecosystem default, not a preference. torchvision.io.read_image and torchcodec both return RGB uint8; BGR is purely an OpenCV artifact. The 7 BGR-needing models keep flipping internally and declare it — the boundary itself stops being BGR.
  • Layout = NCHW — the PyTorch idiom: nn.Conv2d defaults to NCHW, a torchvision Tensor Image is (C,H,W) and a batch is (B,C,H,W), and torchcodec's default dimension_order is NCHW. So no per-call permute.
  • NHWC is a memory format, not a different shape. tensor.to(memory_format=torch.channels_last) keeps the logical (B,C,H,W) shape but stores NHWC physically — which is what NVIDIA Tensor Cores want (fp16/bf16, ~22% faster convs on ResNet50). Reach for it on the GPU/TRT perf path; the API stays NCHW. This is also why the ONNX/rtmlib rows in the table want channels-last — it's a perf choice, not a different contract.
  • dtype = uint8 at the boundary. The 5 normalization schemes differ per model, so normalization is the predictor's job — keep the transfer cheap (uint8) and normalize on-device.
  • On-device. The tensor crossing into a predictor already lives on the GPU; .cpu().numpy() happens only at the Rerun edge.
  • HWC NumPy survives only as an explicit CPU adapter — cv2 affine crops in top-down pose, Rerun overlays — never the hot path.
Ecosystem-confirmed (checked May 2026): RGB + NCHW is the torch convention, not a house style — torchvision read_image returns RGB uint8 CHW; torchcodec defaults to RGB NCHW uint8 and decodes straight to GPU with device="cuda" (NVDEC); channels_last keeps the NCHW logical shape while delivering Tensor-Core speed. The current simplecv readers override all three defaults (cpu / NHWC / BGR-numpy) — they're swimming against the ecosystem.

Decision 2 — loading torchcodec, used properly

  • Already a dependency (pinned >=0.10,<0.11, linux-64). Standardize on it; retire cv2.VideoCapture (10 files) and PyAV (8).
  • Fix the readers: expose device="cuda" (NVDEC decode), dimension_order="NCHW", return RGB uint8 tensors on the GPU — drop the BGR/CPU/NumPy shim. Keep a thin .to_bgr_numpy() adapter only for code still on cv2 mid-migration.
  • Wins: hardware NVDEC decode, frames land on-device (no host→device copy), batched range reads (decoder[a:b] → (T,C,H,W)), fast seeking.
  • Encode side too: reconcile torchcodec encoding with the existing pyvrs-viewer NVENC/AV1 encoder + simplecv.video_encoder so encode is one path, not three.
  • Caveat: CUDA decode needs an NVDEC-enabled ffmpeg build (linux-64, already the repo's GPU constraint). Keep CPU decode for the None-GPU envs (robocap, pyvrs).

Decision 3 — batch-first, for torch → ONNX → TRT leading batch axis, always

  • Result types and predictor I/O are batch-first — a leading batch axis is always present, even when 1. The PyTorch path is then shape-identical to its ONNX/TRT export, so conversion is trivial and engine shapes match what the wrapper already emits.
  • Name the two batch axes: frame/clip batch T (whole-image models — torchcodec hands you this for free) vs instance batch N (persons / detections / hands in top-down models). sam3d-body already folds them (B*N); the contract should label them, not bury them.
  • Export with a dynamic batch axis (dynamic_axes) + TRT optimization profiles (min/opt/max). Today's sapiens2 TRT engine is batch=1 static — the anti-pattern: it forces a per-person Python loop and discards TRT's batched throughput.
  • The repo already proves the payoff: sapiens-coco133 ships an iterable-PyTorch "golden" path and a batched-TensorRT path, with a benchmark asserting a minimum speedup. Batch-first is what keeps that second path clean.
Net — the ImageInput boundary: the predictor contract (§07) takes a foundation ImageInput — RGB · uint8 · NCHW · on-device · batch-first — and each predictor declares its deviations (expects_bgr, wants_nhwc, norm=…, input_size=…, batch_kind=frames|instances). One shared preprocess() applies flip / permute / normalize / resize on-device, once; torchcodec delivers the tensor already on the GPU; and the same shapes flow straight through ONNX and TRT. Color and geometry conversions use kornia (§06).

11Composition & deployment — DAG nodes without lock-in

You want modular and composable, and you're right to be wary of daggr. The resolution: make the predictor the node and keep the transport swappable. Composability comes from the uniform contract (§07) + the shared ImageInput / result types (§08, §10) — not from any one orchestrator. Then the same DAG runs three ways and you only pay the performance cost where you choose to.

In-process hot path

Wire predictors as Python nodes in one process; tensors stay on the GPU between stages — no serialization, no host copies. This is BasePipeline (§07), or daggr with FnNode / graph.invoke(). Use for throughput, batch jobs, and tests.

daggr / Gradio HTTP demo only

GradioNode("http://…") wires running Gradio apps — yours or remote HF Spaces — into a visual DAG. Great for debugging, sharing, Space reuse. But every edge serializes images over HTTP across processes, so it is not the hot path. (Your multiview-calib graph: VGGT + SAM3 + MoGe → align → fuse.)

bubbaloop edge / robot

kornia-org's single ~13 MB Rust binary: Zenoh pub/sub (µs latency), RTSP cameras, Jetson / Pi. Fed by your ONNX/TRT artifacts (§10 · Decision 3); same kornia lineage as your geometry dep (§06). North-star for on-robot serving — not an immediate dependency.

Resolving the daggr worry

  • The worry is real only if daggr is the hot path. HTTP edges + per-node serialization kill throughput. Fix: run the performance path in-process (left column); reserve daggr-over-HTTP for visual/demo composition and remote Spaces.
  • The deeper risk is lock-in — solve it with one rule: src/ never imports daggr. daggr graphs live in tools/graphs/ and point at the package's Gradio apps or call its predictor functions. The package's models/ and api/ carry zero daggr import, so daggr is a swappable consumer and the package stays self-contained.
  • Don't maintain two implementations. The repo's own daggr_proposal.md already names this pain — a daggr graph and a hand-written Gradio app per pipeline, kept in sync by hand. Its proposed graph.as_gradio() / graph.invoke() is the fix: one graph definition → visual canvas, Gradio app, or headless in-process call. Until that lands, write the unit as an in-process Pipeline and expose a thin Gradio app; let daggr wire the apps for demos.
The principle: modularity is a property of the contract, not the transport. You don't lose performance by being modular — you lose it by forcing the hot path across process / HTTP boundaries. Same typed nodes, three transports: in-process on the GPU for speed, daggr for demos, bubbaloop for the edge. (bubbaloop caveat: its documented models are VLMs like Paligemma; arbitrary-model runtime support isn't fully specified yet — treat it as the target the ONNX/TRT work feeds, not a drop-in.)

13Open decisions (only you can make these)

The structure above has a few genuine forks where I have a recommendation but the call depends on your intent. These are worth settling before step 1.

Does simplecv stay one foundation, or split into simplecv-core + simplecv-data?
Today simplecv carries both lightweight primitives (camera params, conventions, Rerun types) and heavy dataset machinery (HoCap/Aria/EPFL loaders, catalog tooling, a 25-file apis/). Capability packages only need the primitives. Recommendation: split — a thin simplecv foundation (types, ops, Rerun, camera) that capability packages depend on, and a separate data/forge package for dataset converters & catalogs (absorbing egoexo-forge, pyvrs-viewer). Keeps the foundation's dependency surface small.
"Make everything PyTorch-based" — how literally?
Largely settled in §06: depend on kornia for GPU geometry, keep simplecv for the rest, and make heavy data (images, depth, masks) torch tensors on-device through the predictor contract while small metadata (K, poses) and the Rerun edge stay NumPy. Several backends deliberately aren't torch — cuVSLAM (robocap), pycolmap (pysfm), the Rust gsplat renderer, DBoW2/ASMK retrieval — and shouldn't be rewritten. Still yours: how hard to pin kornia (conda-forge trails PyPI by a release), and whether to expose kornia types or wrap them behind simplecv dataclasses.
Capability packages vs one mega-package with submodules?
You floated "separate packages like pose-estimation, depth-prediction." Recommendation: separate pixi-environment packages (matches the current per-package env model and keeps GPU/dep stacks isolated — Sapiens, SAM3, and cuVSLAM have very different dep trees). The shared contract lives in the foundation, so packages stay consistent without sharing one environment.
Is consolidation worth disturbing working code at all?
These are example/demo packages — churn risk is real and the payoff is consistency, not new capability. Recommendation: do steps 1–3 (naming + contract + per-package adoption) regardless — they're cheap and high-readability-value. Treat the capability merges (steps 4, 6) as opt-in: only merge a family when you're already doing real work in it, so the refactor rides along with a feature rather than being pure overhead.

Capability families map onto the §04 taxonomy with no new buckets: rf-detr is a detection + seg backend, mammanet a top-down keypoints node, mini-dust3r a multiview backend, and DA3 spans depth + multiview at once (below).

Verdict — the contract holds. Despite a third-party type, two heterogeneous bundles, and a research dict, all four collapse into the same shape once wrapped: construct-by-string → call-with-image → typed result. That collapse is the pattern earning its keep — the wrapper is where upstream chaos goes to die. They don't refute the design; they sharpen three parts of it and settle one open decision.

Three refinements they force

1 · Results must compose atoms + bundles

DA3 and mini-dust3r each return depth and poses and a point cloud (+ splats/mesh) from one call — a flat DepthMap cannot type them. Keep the §08 types as small atoms, then add bundles that hold atoms: MultiviewResult{ views: DepthMap[] · cameras: CameraTrajectory · cloud: PointCloud · splats? }. mini-dust3r already proves it — its result embeds simplecv's PinholeParameters instead of re-rolling cameras. Add optional fields (rf-detr masks?) and an extras hatch (mammanet contact).

2 · ABC for producers, Protocol for consumers both, with roles

You wrap all four by composition — you own none of these classes — so Protocol's "let it fit structurally" buys little. Keep the tiny BasePredictor[InputT, ResultT] ABC: it is the home for shared to(device), the on-device preprocess() (§10), and boundary flags (expects_bgr, needs_bbox), and beartype enforces the typed return. Reserve a @runtime_checkable Protocol for the consumption seam (a benchmark that takes "any depth model") and for rr.AsComponents on the result types.

3 · Factory: split arch from weights keep the Literal

rf-detr selects by separate classes; DA3 by one class, 7 checkpoints; mammanet by config name. Keep the closed Literal + match factory (the curated menu tyro validates) but make it one entry per architecture — push size/checkpoint to a constructor arg. A registry-decorator only pays off for third-party plugins you don't author; you author every wrapper, so don't trade away the static Literal.

The open decision they settle (§13 · "granularity is a dial"): DA3 is a single forward that is simultaneously depth, camera pose, multiview reconstruction, and 3DGS — it openly breaks "one capability → one output type." Don't force it into one bucket: have its wrapper return the composite MultiviewResult and register the same wrapper under several capability factories — get_depth_predictor("DA3") projects just the DepthMap; get_multiview_predictor("DA3") returns the full bundle. That one model now spans both is the concrete argument for folding depth and multiview into a single package.

Per-model wrinkles the adapter must absorb: rf-detr already returns supervision.Detections (decide: re-export it, or wrap it), with mask=None on box-only variants and class names tucked in .data["class_name"]. DA3 / mini-dust3r are multi-output bundles — pointmaps are derived by unprojecting depth with the predicted intrinsics/extrinsics, not a stored field. mammanet emits a sigma (inverse-confidence — flip it at the adapter), contact/floor_contact heads (no standard slot → the extras hatch), and 512 non-skeleton landmarks (an SMPL-X vertex subsampling) that need a length-agnostic Keypoints2D; it also requires a person bbox upstream — i.e. it is a top-down keypoints node that consumes Detections, reinforcing §04's case for detection as its own capability.
